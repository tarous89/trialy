# TrialAgents template authoring standard

Version: 1.3.9

This is the living engineering contract for templates served by TrialAgents. Update it when a verified renderer, lifecycle or host-integration lesson changes. Retrieve the current copy with `read_app_template_guidance(resource:"authoring")`; follow `nextOffset` to the end. The response includes a version and content hash. Packaged plugin examples are not the catalog.

## Required preflight: recurring failures from the first seven packages

These are publication blockers when applicable, not optional styling advice. Apply them before designing screenshots or building the offline preview. Start from the current host contracts and a verified package; do not copy an uploaded candidate's mocks or assume that its tests prove compatibility. These checks preserve freedom to build different apps; they constrain integration, data correctness and truthful behavior, not app category or visual structure.

| Repeated failure | Required prevention | Regression that must pass |
| --- | --- | --- |
| The preview runs but the catalog cannot load or the installed app crashes. | Validate the **whole catalog**, not just the new JSON. Read the current schema in `src/workspace/app-templates.ts`. For `frontend-js`, catalog `source` must not declare `templateConfiguration` or `templateBindings`: `AppTemplates.operation` prepends both. Keep configuration in `options`/`defaults`; inject it once in offline previews. | Discover/read the exact version and digest, prepare through `AppTemplates.operation`, and execute that prepared source in real QuickJS. Do not strip declarations or rewrite source in the test to make it pass. |
| Inputs look usable offline but are disabled in TrialAgents. | Put `data-ui-state` on **each** transient `input`, `select` and `textarea`, including filters, dates and project selectors. Putting it only on the form is insufficient. Give change controls stable `data-action` values and form controls `name` attributes. Use actual `input.event.kind/action/value/form`; named form values are `event.form[fieldName]`, not invented `form.key`/`form.value` events or stripped `data-field` attributes. | Interact with text, number, date, select and textarea controls in the production sanitized frame **with a manifest attached**. Do not remove the manifest or weaken the sanitizer to enable inputs. |
| ChatGPT creates incompatible fields or relationships. | Supply explicit field kinds, `multiple:false` for every scalar, select options, null/empty semantics, required fields, and logical-to-actual mapping. Real field keys obey `^[a-z][a-z0-9_]{0,63}$`; camelCase may be a logical UI key only. Use text for URLs/multiline evidence and scalar UUID references when that is what the renderer consumes. Never assume arrays or relationship objects behave like scalar IDs. | Create the documented schema through the real reviewed database path, save parent records, substitute their receipt IDs into children, and run the template against those records. Test invalid/multiple values without silently coercing them. |
| Typing disappears, selector changes show old data, or errors erase work. | Store each draft change in returned state. Merge submitted named values into that draft, including fields temporarily hidden by layout. Apply scope/project/period selection changes **before** calculating dependent rows and metrics in the same render. Re-read saved layout configuration instead of letting stale local layout win. | Change several controls, rerender, fail a proposal and confirm the draft remains. Change the parent selection and assert the selected label, rows and totals agree immediately. Test Ignore/cancel and reopen. |
| An edit or archive overwrites a concurrent change. | Capture record ID and version when the editor or archive confirmation opens. Carry that original version into `expectedVersion`; never replace it with the version fetched at submit time. A missing edited record is a conflict, not permission to create a replacement. Preserve the draft on conflict. | Open edit/archive at version N, commit an independent update, then submit the old form: no write, clear conflict, retained draft. Apply the same rule to copy-to-existing and reusable-library updates. |
| Denied, missing or truncated data becomes zero, “ready”, or a misleading ranking. | Track completeness per required source separately from row count. Handle `unavailable`, missing bindings/fields, unknown totals, short pages and exhausted read budgets as incomplete. Only a confirmed complete empty result means zero. Withhold authoritative totals/approval/closure that depend on missing evidence; label any supported provisional result explicitly and keep correction controls available. | Test complete-empty, unavailable, missing-field, unknown-total, short-page and over-budget fixtures independently. None of the incomplete cases may claim complete coverage, readiness or absence of dependencies. |
| Parent archive or approval leaves inconsistent evidence. | Check every relevant dependent role, including indirect links and ratings. Require complete authorized dependency reads before claiming there are no live children. Reject orphan references and duplicate logical evidence. Evidence changes must reset/revalidate linked approval; copied records must not inherit protected approval/submission state. Scalar IDs and UI guards do **not** create database foreign-key constraints or protect independent database edits. | Exercise linked/unreadable children, orphan parents, duplicate assessments, copied approvals and changed criteria. Verify an approved decision cannot silently remain valid after its supporting evidence changes through the app. |
| Rows disappear after a fixed slice, or essential actions are absent. | Provide reachable paging for every advertised register, timeline and comparison, including comparisons showing five items at a time. Include creation from an empty dataset and advertised edit/duplicate/archive actions for every relevant record role. Label search/sort scope when reads are bounded. Preserve or clamp each view's page appropriately. | Use more rows than both the display page and read budget. Reach the last displayed page, switch scopes, and create the first parent/child from empty data. Never claim a page is the complete dataset. |
| The layout gear opens a mock, saves nothing, or hides required inputs permanently. | Use native `tracker:layout` and a valid `templateLayoutSchema`. Every advertised order/visibility setting must affect the rendered view or documented drawer, persist via versioned review, and leave bindings/access unchanged. Keep hidden required inputs reachable, for example through an Additional fields control; never make an approval impossible to complete. | Drag screen and field order, review/confirm, reload, then test stale layout and Ignore. Edit a required field that is hidden by default. Verify the actual UI changes, not just the saved JSON. |
| Numbers look plausible but mean the wrong thing. | Define the calculation contract: active versus planned baseline, date boundaries, units, currency, missing values, duplicates and approval criteria. Never sum mixed currencies or relabel an existing amount by changing the currency selector; never count planned hires as current capacity or count one allocation twice. Do not infer a score from missing evidence. | Assert known results from independent small fixtures, including missing/invalid dates, tentative records, duplicate requirements and currency mismatch. Test boundary cases, not just copied implementation formulas. |
| An attractive screenshot still fails save or becomes unusable on mobile. | Run the production design inspector and sanitized browser frame. Meet its current contrast/font thresholds; keep one page scroll and constrain wide matrices to labelled horizontal-scroll regions. Keep menus, toolbar actions, dialog close/save and long content reachable. | Pass the design gate; inspect desktop/mobile screenshots and exercise 320/390/768/1100/1440px widths, long labels and open drawers/menus. A screenshot alone is not interaction verification. |
| Automation prose invents capabilities or implies activation. | Put complete setup instructions in MCP-returned catalog documentation, not only ZIP/README files. Read the current automation guide for typed triggers, supported placeholders, destinations and recipient rules. Use fixed email text when dynamic interpolation is unsupported. Specify scope, expiry, deduplication, output/write authority, partial/failure handling and the no-automation path. `no_update` permits silence only with complete coverage and an approved quiet policy. | Dry-run examples against synthetic complete/partial/duplicate evidence. Confirm that app loading and draft retention require no scheduler/email calls. Never treat metadata, an Enabled flag or a local test as a successful live run/delivery. |

### Publication sequence and required evidence

1. **Define the real setup contract first.** Inspect the current catalog, field schema, frame event contract, native layout and reviewed mutation APIs. Put all information ChatGPT needs to create/use/edit the app in `instructions` and `documentation`; a reference to a repo-only schema file is insufficient for an MCP consumer without repository access. Keep full schema/mapping examples alongside the source as additional maintainer evidence.
2. **Validate metadata before UI work.** Current limits include a 300,000-byte catalog file, 180,000-character source, 20,000-character instructions, 6,000-character documentation prose fields, at most five documentation examples, and required `tasks.promptExample` even for `mode:"none"` (explain the no-task path). Consult the actual schema before publishing rather than treating this list as a replacement for validation. One malformed JSON entry can break discovery of the whole catalog.
3. **Prove the host boundary.** Use the actual catalog preparation, QuickJS, reviewed database fixtures and production frame with bindings/manifest. The offline preview must use the same source/CSS and event shape; it is a demonstration, not the acceptance authority. Test mocks must include denied/partial reads and stale versions. They must not silently remove the failure being tested.
4. **Package reproducibly.** Store canonical source, CSS, metadata, exact schema/mappings, fictional demo/HTML preview, setup/automation instructions and QA under `templates/source/<slug>/`. Generate `templates/apps/<id>-<version>.json` deterministically; wire its builder's `--check` into the repository build. Do not ship contradictory older generated files or claim that a ZIP on its own is registered. Discover the new version through the actual catalog loader before committing the release.
5. **Record what passed.** Run the affected catalog/runtime/database/browser checks and build/type checks. Keep behavioral regression tests for the failures above. Record commands, outcomes, fixture scope and unverified host/deployment/automation boundaries in package QA. Failed, cancelled or timed-out tests are **not passes**; investigate relevant failures and report unresolved verification limits. Re-running until a flaky pass or forcing exit does not turn incomplete assertions into evidence.
6. **Preserve existing users.** Publish a new semantic version; do not rewrite released catalog contracts or silently migrate saved apps. Repository commit, deployed MCP catalog availability, connected ChatGPT acceptance, saved app receipt, runner readiness and delivered email are separate verified outcomes. Claim only the outcomes actually checked.

Evidence for these rules comes from the corrected Cash Runway, Hiring, CRO Oversight, Resource Planning, RFP, Site Feasibility and CRO Selection packages. Working regression examples are `tests/cash-runway.test.ts`, `tests/hiring-template.test.ts`, `tests/cro-template.test.ts`, `tests/resource-template.test.ts`, `tests/rfp-template.test.ts`, `tests/feasibility-template.test.ts`, `tests/selection-template.test.ts`, their database integration fixtures, and `scripts/test-*-browser.ts`. Use their **tested patterns**, not a blind copy of domain calculations. These rules apply to new templates and requested revisions; they do not authorize automatic changes to existing saved apps.

## App account and TrialAgents branding guardrails

Apps are internal tools accessed through the existing TrialAgents account. Do not add app-specific sign-in, signup, logout, password reset, account/profile management, credential storage, OAuth, identity providers or a second user/seat system. Use the platform's account connection and existing app, table, field and record permissions. Business contacts and assignees are data, not new login accounts. “No app authentication” does not remove TrialAgents authentication or make an app public. Public/team sharing, when explicitly requested, uses the platform's existing reviewed sharing controls.

TrialAgents branding inside app content is optional; the platform already supplies its watermark. Whenever a TrialAgents logo or branded wordmark is used, include the real TrialAgents icon and make the entire logo a link to **https://platform.trialagents.com**. Use the supplied black icon on light backgrounds and white icon on dark backgrounds, preserving its shape, colors and aspect ratio. Do not substitute text alone, initials, a generic symbol, a drawn/CSS/SVG approximation or another product's logo. The link must not point to an app route, an Intel site or an authentication page. Give the link an accessible name, such as “TrialAgents”.

Official assets: `https://platform.trialagents.com/trialagents-mark-black.png` and `https://platform.trialagents.com/trialagents-mark-white.png`; the same files are packaged under `plugin/trialy/assets/` and `public/` in the source repository. The current generated-HTML sandbox accepts embedded raster data images, not remote image URLs. Use the exact official PNG bytes as a data image when adding an in-app logo; never loosen the sandbox or invent replacement artwork. If an asset cannot be embedded within runtime limits, omit optional in-app branding and retain the platform watermark. Do not duplicate, cover or replace that watermark.

Before preview/save, verify that there are no generated account/authentication controls or credential fields, that any TrialAgents logo includes the official visible icon, and that its actual clickable destination is exactly `https://platform.trialagents.com`. Check both light/dark contrast and narrow/desktop layouts. Preserve all backend permission checks.

## Optional app sections and automation configuration

Every app keeps its backend app-level access boundary. Optional configuration must never prevent a saved app from opening or ordinary records from loading. Do not rewrite existing apps to add metadata. Preserve IDs and policies during requested revisions.

- **Access:** the existing Projects section shows projects and apps by default. Apps expand into optional parts, using the same pattern as Database → tables → columns. For standard tracker record tabs, use a stable unique `accessId`, for example `tabs:[{accessId:"companies",name:"Companies",typeId:<saved or temporary UUID>,columns:[{field:"name"}]}]`. Changing labels or order preserves accessId. Tabs inherit the app policy and can only narrow it. Missing accessId is valid and keeps app-level access. Custom arbitrary source has app-level access until a proven section boundary is available; never implement security by hiding HTML. Protected standard tabs cannot attach functions/assets or copy restricted bindings to a new unrestricted tab. Independently permitted Database/other-app paths remain independent.
- **Automation:** consider useful ongoing work, but zero automations is valid. Save the app first, then configure accepted research through `prepare_app_monitoring` or deterministic/email work through `prepare_app_action`. Reuse existing IDs and a stable app-specific authoringKey on retries. Consult `list_app_automations`, `read_app_automation`, and `read_app_automation_guide`. Research uses the shared ChatGPT runner; email always runs through TrialAgents. Do not create a ChatGPT task per app or send emails from ChatGPT. A configuration failure leaves the saved app intact.
- **Setup:** quietly check `read_automation_setup` at first supported use, every app creation, adding an automation and reconnection/explicit repair. Complete missing already-authorized setup where supported; otherwise suggest the resumable handoff. Respect declined setup and deliberate pauses. Reuse a verified subscription; never fabricate host IDs or callbacks. Prefer a supported Work chat, high reasoning, and the latest highest-capability model available in the user's subscription. Current task tools have no model/reasoning parameters: report the requested preference separately from observed host settings, and never claim an automatic model upgrade.
- **Documentation:** each new template documents purpose, stable sections/inheritance or app-only access, optional data/connector bindings, automation mode (`none` is legitimate), executor, timing/timezone, exact prompt or action, sources, destinations, expiry/limits, write permissions, no-result/failure behavior and disable/edit/history. Include both an automation example when useful and a no-automation example. User management and ChatGPT use the same versioned definitions and review path.
- **Continuity:** definitions stay listed and editable when disabled. Saving does not re-enable them. No standalone automation Delete action. No automation reads on app loading, navigation or ordinary saves; no scheduler failure banners inside generated apps. Never erase records or local input on task failure. Run outcomes belong in platform Logs; setup diagnostics stay in the private connection/setup flow.


## Automation management and Logs presentation

Keep the platform Automations page full width and limited to app-linked definitions (including database-triggered actions). Each item shows its linked app, an explicit Enabled or Disabled text badge, Trigger or Scheduled with readable frequency/timezone, and the research prompt or typed action instructions, with Disable/Enable and Edit. Update the badge from the confirmed saved state after a successful control change; retain it on failure. Enabled describes the definition, not verified runner readiness, successful execution or email delivery. Keep execution outcomes in Logs and show both states clearly on desktop and mobile. Load full configuration only on Edit. Preserve validation, exact review and disabled state. A genuinely empty list has only a concise empty message, without filters, pagination, setup controls or run history.

The shared daily ChatGPT check is backend infrastructure independent of per-app definitions. Do not duplicate it as an automation row or embed its settings under the list. Use the existing private setup review and connection tools. Direct users to Automations for instructions and to Logs for run statuses. Logs filters by app, project, outcome and category; CSV uses the same filters. New writes carry verified app context; older unattributed events are not guessed from shared database membership. Private prompts, payloads and diagnostics are not released by log metadata.

Additional filters belong in normal document flow, alongside the main row when space allows or wrapping into a second row. Avoid overlapping popovers or vertically stacked dropdown panels. On narrow screens allow fields to wrap, keep labels/inputs inside their controls, and preserve a single page scroll owner. Apply these rules to both standalone and embedded surfaces.

## Required configuration handoff for every future template

Use the existing catalog documentation fields; the following is an authoring checklist, not new JSON fields accepted by the API. Read the current tool/schema contracts rather than copying a complete dispatcher or stale payload into each template.

| Existing documentation field | Required content |
| --- | --- |
| `dataContract` | Saved versus local data, authorized bindings and relationship identities; optional stable section IDs, inheritance, and the limits of supported section isolation. State when there is no database or only app-level access. |
| `interactionContract` | Supported app controls and the link to platform Automations for management; no duplicate automation settings store or required automation tab inside the generated app. |
| `lifecycle` | Stable app/section/automation identities, reviewed edits, receipt reconciliation, disabled-state preservation, archive suspension and no automatic resume/copy activation. |
| `tasks` | `mode: none` or `optional`; classify each useful objective as ChatGPT processing, a standalone TrialAgents email/action, or an approved processing-to-email chain. Metadata is a recommendation, never an active definition or authorization. |
| `tasks` and `examples` | Concrete trigger, timezone, source eligibility, exact research instructions/action, output destination, deduplication, coverage, scope/expiry/limits and no-result/completion criteria. Provide a no-automation path. |
| `limitations` | Unsupported custom-section controls, pending host activation, requested versus verified model settings, external delivery dependencies and any manual fallback. |

Choose the smallest useful automation arrangement; templates may offer these choices without requiring any of them:

- **No automation:** a static checklist or calculator opens and works with app-level access, no runner, connector or database if not needed. Never add a token recurring task just to satisfy an example.
- **Research:** save the app, reuse the owner/workspace runner, prepare one app-linked monitor with an explicit daily/weekly/monthly, one-time, after-success, record-date or database-change trigger supported by its schema. Define authoritative sources, inclusion/exclusion, evidence dates/links, deduplication, authorized destination and completion conditions. A schedule's due time is not a promised completion time.
- **Standalone email:** prepare one separately approved email action on a daily-or-slower calendar schedule, on entry creation, or on an explicit database field transition. The backend dispatches it without a ChatGPT send decision. Select the owner by default and add only explicitly approved registered team members with current app/data access. An address stored in a record is not recipient permission.
- **Research plus email:** prepare the monitor and a separately approved TrialAgents completion action with a manual trigger. The engine invokes it after the required successful research result. A report with no new findings may still be `completed`; `no_update` permits silence only when the reviewed notification policy allows it. Do not give email a second independent schedule, rerun successful research after delivery failure, or send through ChatGPT email tools.

Use these examples when they fit the requested app:

| User intent | Template authoring expectation |
| --- | --- |
| New lead signals, email at most daily | Schedule ChatGPT research daily, save authorized findings with stable signal identities, and use `no_update` when the approved policy permits silence. Attach a separately approved completion email with a manual trigger. Do not give that email an independent schedule. |
| An existing app update every two days | Use one email action with a calendar schedule every two days and fixed approved recipients. Email templates do not implicitly scan a table or perform research; add separately approved processing if current analysis is needed. |
| A new entry needs processing, then another person must review it | Trigger ChatGPT processing from the entry and save its authorized result plus an explicit status transition such as `review_status: pending → ready`. Configure the separate email rule to fire on that transition. Processing can run multiple times daily; delivery limits apply independently. Do not also attach a completion email for the same handoff. |
| No ongoing work is needed | Save a fully usable app with no automation. Do not invent a schedule or recipient list to satisfy the template. |

Before authoring a database rule, inspect the actual table, field type and existing workflow values. Reuse a meaningful status/assignee/revision field rather than creating an arbitrary send-email flag. Add or change schema only within the user's authorized scope. Trigger on a transition into the condition, not every write while the condition remains true. A resolved or deleted entry must not generate a stale notification. Automated writes do not recursively trigger ChatGPT research; use the supported explicit completion linkage when a processing chain needs a follow-up.

Treat source selection, eligibility, deduplication, output destinations and no-result behavior as part of the instructions and approved backend configuration. Keep the user form minimal: linked app, name, schedule or named database condition, instructions or message, and recipients. Do not generate separate digest/report modes, duplicate app settings, or controls for quotas, retries, scopes, catch-up, anchor dates or internal IDs. Use existing app access and approved write scopes; an automation never grants itself broader access. Preserve hidden values and disabled state when revising a definition.

When setup tools/events are missing, keep the app saved and report that automation setup is pending. Check whether the host catalog needs a custom-connection metadata refresh and a new Work chat. Consult the current setup guide; do not fabricate tool names, subscription IDs, callbacks or model parameters. Infrastructure secrets and operator key-copy procedures never belong in a generated app or a user's research prompt.

Report these outcomes separately: app saved; access configured or inherited; automation definition saved and enabled/disabled; connection readiness; next eligible run; actual completion/write receipts. A successful app save is not an automation success. A failed automation is not a failed app.

## What the Vivid tracker taught us

| Working pattern | Apply it to future templates |
| --- | --- |
| One tested renderer, many configurations | Separate the reusable renderer, theme, configuration schema and domain examples. Change labels, columns and options through configuration; avoid copying and editing the full renderer for each app. |
| A complete reference, not a screenshot alone | Keep canonical HTML/CSS, component catalog, configuration examples and interaction contracts together. Test actual rendered screens. |
| Bound controls | Map every displayed or editable business field to an authorized table/field identity, schema version and read/write mode. Labels are not database identities. |
| Real end-to-end interactions | Specify what every control does, what it changes, how it is approved and how it fails. A styled button is not a completed feature. |
| Explicit state ownership | Distinguish local inputs, unsaved app previews, published source and committed database records. A successful render is not a save. |
| Stable application identity | Revise the existing app ID and exact version. Retry one creation with its original request key. Do not create replacement apps to repair a draft. |
| Shared surfaces | Use the same runtime and contracts in the platform, standalone app, public share and ChatGPT extension. Host navigation and business actions are different contracts. |
| Small, verified updates | Retain the current usable view until a replacement succeeds. Keep input, route and scroll state during transient failures. |

These are reliability and design defaults. They do not restrict users to trackers or fixed categories. Use custom source when a template does not fit; database permissions, approvals, logs and the execution sandbox remain mandatory.

## Required template package


Publish a catalog JSON under `templates/apps/<id>-<version>.json`. Keep IDs stable, use semantic versions, and publish a new version instead of rewriting a previously released contract. The raw-file digest protects preparation against catalog changes. Existing apps retain their saved source and configuration; catalog updates never silently migrate them.

Every current template must contain:

- `id`, `version`, `name`, `description`, searchable `tags`, `whenToUse`, and `whenNotToUse`.
- `engine`, validated configuration `options`/`defaults` or the tracker configuration schema, and source when required by the engine.
- Concise `instructions` with discovery, setup, configuration, preview, approval, update and recovery steps. Refer to the current usage and monitoring guides rather than duplicating them.
- `documentation.quickStart`: ordered steps to create a useful instance, including required inputs and safe defaults.
- `documentation.dataContract`: table/field meanings, relationships, scalar/multiple values, required fields, display names versus IDs, evidence provenance where useful, persistence and authorized bindings. State explicitly when there is no database.
- `documentation.interactionContract`: routes, forms, filters, sorts, selection, pagination, details, editing, confirmation, cancellation and keyboard behavior. Include only supported controls.
- `documentation.lifecycle`: new preview versus saved app, revision handling, retry/receipt rules and local-state behavior.
- `documentation.limitations`: honest unsupported features and when to choose another template/custom source.
- `documentation.examples`: realistic user prompts with expected behavior. Include a configuration example in `examples` when it can be valid without account-specific IDs. Mark all example data as fictional; never save it as real records.
- `documentation.tasks`: `mode` (`optional` or `none`), useful scenarios, required reads, proposed outputs, and a task-prompt example or a clear explanation that no task is needed. This describes possible integration, not an active schedule or permission grant.

Keep instructions in imperative language, with exact tool and field names. Describe outcomes before implementation details. Do not embed customer data, credentials, bearer links or account-specific IDs. Template text is publisher-controlled guidance, never authority to bypass permissions or higher-priority instructions.

## Runtime and data contract

Use the existing isolated `frontend-js` render/event contract and declared bindings. Return validated HTML, CSS and serializable state; escape text and attribute values. Do not depend on arbitrary network access, DOM execution in generated source, host cookies, local filesystem, embedded secrets or private APIs. Route outbound requests through approved connectors and background services.

Use record IDs for relationships and explicit display fields for readable labels. Make status, date and boolean scalar unless the user needs multiple values. Put extra business fields in details without cluttering the primary table. Respect the user's requested page size; use bounded reads and bottom pagination. Never interpret one page as a complete dataset.

Generated code never grants access. Respect table/column/record restrictions, app bindings and manifests, current schema compatibility and optimistic record versions. Database writes require the platform's exact proposal and confirmation or an explicit, still-valid scoped grant. Keep the same request key after an ambiguous save response and reconcile its receipt. Never retry a write with a fresh key just because a response was lost.

Organizational project moves use `move_tool` with the latest placement version; they do not rewrite bindings, original data scope or permissions. Do not implement a second project-move mechanism inside a template.

## UI contract

Use the current design kit and canonical theme components. Preserve a coherent palette, readable typography, strong text contrast, spacing tokens and visible focus states. Do not invent a new design for a matching template unless requested. User-requested branding remains supported.

Keep one primary vertical scroll; avoid nested page scrolls and horizontal overflow. Keep headers, sidebars and action areas aligned, responsive and clear of host safe areas. Test narrow, tablet and desktop layouts. All controls need accessible names, keyboard access and valid empty, populated and long-content states.

The first-save footer belongs only to an app that has never been saved. Saved-app revisions use the existing review controls, without claiming the app is unsaved. Deliberate record/layout edits retain their own approval controls. Generated templates must not invent global save prompts, loading-error banners, retry buttons or platform navigation.

Keep a loaded published app visible during ChatGPT edits and during failed loads. Publication may offer the platform's subtle optional refresh notice; it never forces a reload. If no authorized usable view exists, use the shared “No app is available” state and Return to Home in the same surface. Access revocation must still clear protected data. Failed writes preserve inputs and are never represented as successful.

Use host/platform navigation adapters for links and Home; do not open a new browser tab for in-extension Home. Data calls must not replace the visible workspace through tool-result metadata. Present only complete previews; avoid repeated intermediate renders.

## Responsive interaction contract

Keep the primary data toolbar on **one line**: a shrinkable search input and the main action (for example, Add record). When the remaining controls do not fit, move secondary filters and sorting into a labelled **Filters** disclosure. Measure available container width and actual control widths; do not rely only on device breakpoints. The action must not fall onto a second row. Shorten its visible label at very narrow widths while retaining its accessible name. Show the active-filter count on the disclosure.

The disclosure is local UI: opening it must not fetch data. Keep it within the viewport, allow its contents to scroll, preserve selections and search when resizing, expose `aria-expanded` and `aria-controls`, and support keyboard navigation, Escape with focus return, and outside-click dismissal. Keep an overflow-safe, usable fallback for older frame code and static design inspection; enable collapsible controls only when their frame handler is present. Do not hide controls permanently to make a screenshot fit.

Use one main vertical scroll. Wide data tables may scroll horizontally inside their own labelled region; the page and action toolbar must not overflow horizontally. Keep tab navigation reachable, wrap long titles and values, stack overview cards as needed, and let details/settings fit the viewport without covering their close/save actions. Test 320, 390, 768, 1100 and 1440 CSS pixels, long labels, several active filters, narrow host containers and zoom/reflow. Fewer controls should remain inline when there is room. Preserve selection, inputs, scroll and business state across responsive changes.

## Performance contract

Use the standard tracker configuration and shared renderer for matching record workflows; copying/forking renderer source prevents shared fixes from reaching that app. Custom source remains supported but must meet the same measured responsiveness expectations. Prefer scoped bindings for new apps; never widen or silently change existing access to improve performance.

Load one bounded active page, counts for overview totals, and bounded optional next-step samples. Respect control and payload limits even when a requested page size is larger. Do not fetch every row, every hidden tab or every detail merely to paint navigation. Page-local search/sort must be described honestly. Use readable labels and all authorized detail fields without loading unbounded records.

For the shared runtime, preserve its instance-local authorized snapshots, bounded neighboring prefetch, identical in-flight read coalescing and access/version invalidation. Cache keys must distinguish app, version/view, route, filters, page and state. Never share data across users or apps, cache mutations, extend permission lifetimes, or skip final freshness checks for speed. Server permission/schema reuse is restricted to one request and rechecked before releasing data; records and counts remain uncached on the server.

After a reviewed layout save, read the saved component with `includeOutput:true` and use that output directly. Do not issue another serial initial render. Keep confirmation, current permissions, optimistic versions and the real save receipt. Never simulate a successful save to remove a loading delay.

Measure realistic complexity and cold/warm behavior: at least four tables, long labels, several filters and 12–28 fields per table, including hidden detail fields. Test a user click while prefetch is still pending, delayed host requests, repeated tab changes, page changes, successful layout reload and concurrent access changes. Set query-count/request-count budgets against a verified baseline; record local timings as diagnostics, not production guarantees. Re-run these checks when publication, access or runtime code changes. Consult [the measured tracker read path](../docs/tracker-performance.md) before adding another cache or timeout.

## Optional tasks and services

Recurring research, analysis and reporting can benefit any app. Declare task opportunities in metadata, not hard-coded template schedules. See `read_app_template_guidance(resource:"usage")` and `read_app_automation_guide` for shared-runner setup (legacy monitors retain `read_app_monitoring_guide`).

Use platform background actions for deterministic recurring, dated or database-triggered operations. Use the shared ChatGPT runner for research/reasoning when the host supports events. Instructions and executable timing live in TrialAgents; never create a task per template. Use durable connector jobs for LLM/API calls that outlast interactive request limits. Notifications use the platform email service with reviewed recipients and purpose. Never embed provider keys or send emails directly from a template.

A template must work fully without a task. Never wait for automation status before showing or saving the app; failures belong only in owner-authorized Logs or private setup diagnostics. Test callback, scheduling and research failure while the app retains its current frame and unsaved input. Task creation, reads, writes, delivery and paid/external actions each need their own applicable authorization. Do not imply that a task was activated merely because template metadata includes a schedule suggestion.

## Acceptance and maintenance

Before promoting a template version, verify:

1. Catalog discovery, exact-version read, configuration validation and digest checks; representative prompts choose the right template, including a non-fit case.
2. A fresh preview, save, reopen, correction of the same preview, lost-save-response recovery and revision of the same saved app. No duplicate apps or example records.
3. Each advertised interaction against real backend fixtures, including next/previous pages, filters, relationships, edits, cancellation, write conflicts and permission revocation.
4. Platform, standalone and host-bridge integration at 390, 768 and 1440 pixels; inspect screenshots for clipping, contrast, spacing, footer collisions and focus. Also run the real ChatGPT host when available and disclose when only the bridge harness was tested.
5. Temporary load failures, outdated tool results and publications retain the current view. No available view shows only the shared empty state and in-surface Home action. Test a failed refresh with unsaved input.
6. If task support is advertised, dry-run the suggested prompt with scoped synthetic data. Test duplicates, no findings, partial coverage, revoked/expired permission, source failures and missed occurrences. Verify a real scheduled run separately before claiming live execution.
7. For advertised email workflows, verify a burst of changes coalesces, obsolete work and revoked recipients cancel, ordinary delivery limits defer without disabling the rule, and an email failure does not rerun processing. Reuse the platform guardrail suite; never send real bulk mail as a template test.
8. Test omitted section metadata and no automation; deny/read-only section rules across rename/reorder; disabled-definition editing; archive/restore; duplicate setup attempts; and setup/task failure with a usable published app and retained local input. Existing apps require no retrofit.
9. Build/type checks and the affected backend/browser suites. Keep regression tests for failures discovered in use; do not merely assert that implementation strings exist.

Record each lesson as a reproducible failure, the contract it changes, its regression test, applicable versions and migration impact. Keep template-specific docs beside the template and shared rules here. Review guidance changes with source changes. Changes to the server-served catalog/guidance ship through the repository deployment; packaged plugin skills or manifests require their own package release when changed.

Manual automation creation: Add automation opens one full-width page with horizontal ChatGPT and Email tabs and the form immediately visible. Preserve each tab's draft. Show linked app, name, schedule/trigger, research instructions, or email subject/message and recipients. Use app-bound named table choices; never expose raw record/table IDs, JSON scopes, allowed fields, execution limits or advanced configuration. New email automations include the owner by default and allow adding app-authorized team members. Existing recipients and hidden configuration must survive edits. New research configurations use inheritAppAccess:true, current app-bound read fields and only existing approved ongoing write scopes within the app; revalidate current app access at execution. This never creates write grants. Keep review human-readable (including authorization expiry), keep backend validation and exact confirmation, and preserve input on failure. Email creation remains available if shared ChatGPT setup is unavailable; research reuses the existing shared runner without claiming subscription activation. Apps never depend on this editor or scheduler availability.


## Simple email notifications

Email automations have one delivery step, separate from ChatGPT/functions/connectors. Use daily/weekly/monthly calendar schedules (every N days/weeks/months), or entry creation/an explicit field transition. No subdaily email intervals or broad “any update” notifications. The backend waits two minutes after relevant changes, combines pending work, rechecks current state/access, and cancels obsolete notifications. It enforces one app email per normalized recipient per rolling hour across TrialAgents and 15 recipient deliveries per account per rolling 24 hours. Calendar email also has one slot per rule/recipient/local date. Extra work waits; only abnormal queue growth suspends a rule. Recipients must be explicitly selected registered team members with current app/data access; database address columns never authorize bulk mail. Research may run several times daily independently of email limits. Do not create report/digest modes, expose quota/retry controls, or use ChatGPT email tools/connectors to bypass these rules.

The editor exposes linked app, name, schedule or database condition, instructions/message and recipients. Keep timezone (shown as help text), anchors, scopes, expiry defaults, source policies, catch-up and delivery limits in backend configuration. Preserve hidden values and disabled state on edits. See [notification scope](../docs/scopes/NOTIFICATION_GUARDRAILS_2026-11-01.md) for rollout and verification.

## Custom template layout and reviewed draft forms

For catalog `frontend-js` apps, declare a single-line JSON `const templateLayoutSchema={screens:[{id,label}],groups:{group:[{id,label}]}};`. Use stable presentation keys. The **prepared/saved app source's host-injected** leading `templateConfiguration` JSON carries `heading` and a stringified `layoutProfile` with `heading`, `tabs`, `cols` and `visible`. The native host reads these declarations without executing app source; the gear emits `tracker:layout`. `prepare_tool_layout` accepts `customLayout` with the existing component ID/expected version and no data-mapping changes. Review/Confirm persists only presentation configuration. Reject unknown/duplicate identities and all-hidden screens; retain source logic, manifest, bindings, assets, execution and access. Read saved configuration on each render so old UI state cannot override a newly saved layout. Native handles support dragging and keyboard/touch source/destination selection. Templates without this declaration keep the existing ChatGPT source-edit fallback.

Custom forms may collect transient proposal drafts using `data-ui-state` on each input/select/textarea (not only the form) and stable `data-action` values. Retain draft values in returned state on change; submit an exact `records.propose` change and use the trusted outer confirmation. This marker permits input interaction only; it never grants writes or changes manifest/access checks. Do not label a draft or proposal as saved. Existing-record drafts retain the record version from when editing began; concurrent edits must fail rather than overwrite. Direct connected cell editing continues to use declared `controls`/slots. Test forms in the sanitized production frame with a manifest attached, not solely in standalone HTML.

Cash Runway's complete source package and valid scalar schema/mapping examples are in `templates/source/cash-runway/`; its catalog JSON is regenerated with `node scripts/build-cash-runway-template.mjs` and checked by the build. Treat source URLs and multiline text as database `text`, and map logical camelCase names to real lowercase field keys.
