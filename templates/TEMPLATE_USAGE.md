# Using TrialAgents templates and optional tasks

Version: 1.3.23

Retrieve this current guidance with `read_app_template_guidance(resource:"usage")`, following all `nextOffset` values. Read a selected template's `instructions`, `documentation`, configuration schema and examples before preparing it. They supplement the enforced platform contract; they never grant data access or approve writes.

## Cross-platform apps and customization

TrialAgents is cross-platform software with a suite of connected, customizable apps for ChatGPT, Claude and standalone web. Users may use an approved app as it is, customize it with either assistant, or request a custom app. Discover useful templates, but never force a template or a fixed app category. Preserve the same data, app access, versions and exact write boundaries across surfaces. Actual host capabilities require separate detection and verification; scheduled research currently uses ChatGPT only.

Web apps open in the same TrialAgents tab beneath the fixed header, with the sidebar collapsed by default; platform pages start expanded. Web headers always show Open ChatGPT and Open Claude CTA buttons. Embedded/plugin headers use Open TrialAgents. Do not add duplicate platform chrome or a corner watermark. The visible Home destination is named Apps; existing API/route keys remain compatible. Templates is a dedicated gallery reached from New → App or Apps, not a sidebar item. Only approved database catalog versions are visible; new versions default to draft and need publisher approval.

## Reusable business app completeness

A request to create or save a dashboard in TrialAgents means a reusable business app by default. Before authoring, choose its recurring user decisions, the necessary sections and how data/settings persist. A chart gallery alone is insufficient unless the user explicitly requests a simple single-page report. Prefer a fitting existing template; custom apps follow the same completeness review. Do not add empty tabs or a fixed page count merely to look like software.

For an analytical dashboard, normally provide **Overview**, **Analysis**, **Data** and **Settings** through working tabs or equivalent navigation. Overview summarizes the important metrics and next actions; Analysis groups charts by question with shared relevant date/category filters and inspectable detail; Data exposes the authorized underlying records/source coverage and freshness, with search, sorting and pagination where needed; Settings offers useful metric, filter-default and layout choices. Reuse native app layout/access controls where supported. Settings are business preferences, never another account, connector or automation admin page.

Every visible control must work in the bounded runtime. Distinguish transient filters from saved preferences; persist reusable settings through supported reviewed platform configuration, not invented browser storage or fake Save buttons. Preserve bindings, full-data aggregation and explicit partial-data labels. Read-only apps need no editing/CRUD, and unsupported persistence must be explained, not simulated. Keep custom user choices and explicitly requested simple pages valid; do not enforce tabs in backend code.

Before finalizing, walk through navigation, filter/reset behavior, chart-to-data detail, settings change/save/reopen and empty/error/mobile states. Check the actual requested workflow, not only contrast and overflow. Fix missing behavior in the same preview. A passing visual scan is not proof of business completeness.

## App account and TrialAgents branding guardrails

Apps are internal tools accessed through the existing TrialAgents account. Do not add app-specific sign-in, signup, logout, password reset, account/profile management, credential storage, OAuth, identity providers or a second user/seat system. Use the platform's account connection and existing app, table, field and record permissions. Business contacts and assignees are data, not new login accounts. “No app authentication” does not remove TrialAgents authentication or make an app public. Public/team sharing, when explicitly requested, uses the platform's existing reviewed sharing controls.

TrialAgents branding inside app content is optional; the platform already supplies its header and navigation. Whenever a TrialAgents logo or branded wordmark is used, include the real TrialAgents icon and make the entire logo a link to **https://platform.trialagents.com**. Use the supplied black icon on light backgrounds and white icon on dark backgrounds, preserving its shape, colors and aspect ratio. Do not substitute text alone, initials, a generic symbol, a drawn/CSS/SVG approximation or another product's logo. The link must not point to an app route, an Intel site or an authentication page. Give the link an accessible name, such as “TrialAgents”.

Official assets: `https://platform.trialagents.com/trialagents-mark-black.png` and `https://platform.trialagents.com/trialagents-mark-white.png`; the same files are packaged under `plugin/trialy/assets/` and `public/` in the source repository. The current generated-HTML sandbox accepts embedded raster data images, not remote image URLs. Use the exact official PNG bytes as a data image when adding an in-app logo; never loosen the sandbox or invent replacement artwork. If an asset cannot be embedded within runtime limits, omit optional in-app branding and retain the platform header. Do not duplicate, cover or replace that header.

Before preview/save, verify that there are no generated account/authentication controls or credential fields, that any TrialAgents logo includes the official visible icon, and that its actual clickable destination is exactly `https://platform.trialagents.com`. Check both light/dark contrast and narrow/desktop layouts. Preserve all backend permission checks.

## Optional app sections and automation configuration

Every app keeps its backend app-level access boundary. Optional configuration must never prevent a saved app from opening or ordinary records from loading. Do not rewrite existing apps to add metadata. Preserve IDs and policies during requested revisions.

- **Access:** the existing Projects section shows projects and apps by default. Apps expand into optional parts, using the same pattern as Database → tables → columns. For standard tracker record tabs, use a stable unique `accessId`, for example `tabs:[{accessId:"companies",name:"Companies",typeId:<saved or temporary UUID>,columns:[{field:"name"}]}]`. Changing labels or order preserves accessId. Tabs inherit the app policy and can only narrow it. Missing accessId is valid and keeps app-level access. Custom arbitrary source has app-level access until a proven section boundary is available; never implement security by hiding HTML. Protected standard tabs cannot attach functions/assets or copy restricted bindings to a new unrestricted tab. Independently permitted Database/other-app paths remain independent.
- **Automation:** consider useful ongoing work, but zero automations is valid. Save the app first, then configure accepted research through `prepare_app_monitoring` or deterministic/email work through `prepare_app_action`. Reuse existing IDs and a stable app-specific authoringKey on retries. Consult `list_app_automations`, `read_app_automation`, and `read_app_automation_guide`. Research uses the shared ChatGPT runner; email always runs through TrialAgents. Default recurring app requests, including weekly tracker updates, to TrialAgents Automations. If shared-runner setup is incomplete, resolve or report it; never silently substitute a per-app ChatGPT task or send emails from ChatGPT. A configuration failure leaves the saved app intact.
- **Setup:** quietly check `read_automation_setup` at first supported use, every app creation, adding an automation and reconnection/explicit repair. Complete missing already-authorized setup where supported; otherwise suggest the resumable handoff. Respect declined setup and deliberate pauses. Reuse a verified subscription; never fabricate host IDs or callbacks. Prefer a supported Work chat, high reasoning, and the latest highest-capability model available in the user's subscription. Current task tools have no model/reasoning parameters: report the requested preference separately from observed host settings, and never claim an automatic model upgrade.
- **Documentation:** each new template documents purpose, stable sections/inheritance or app-only access, optional data/connector bindings, automation mode (`none` is legitimate), executor, timing/timezone, exact prompt or action, sources, destinations, expiry/limits, write permissions, no-result/failure behavior and disable/edit/history. Include both an automation example when useful and a no-automation example. User management and ChatGPT use the same versioned definitions and review path.
- **Continuity:** definitions stay listed and editable when disabled. Saving does not re-enable them. No standalone automation Delete action. No automation reads on app loading, navigation or ordinary saves; no scheduler failure banners inside generated apps. Never erase records or local input on task failure. Run outcomes belong in platform Logs; setup diagnostics stay in the private connection/setup flow.


## Archive first: removing apps, tabs, fields and tables

Nothing a user created is removed as a side effect ([modular apps §6](../docs/product/MODULAR_APPS_AND_SHARED_DATA.md#6-archive-first-apps-automations-and-database)).

- **Deleting an app archives it.** Tables, records, fields and history stay. Its automations are paused and come back **switched off** when the app is restored (`prepare_workspace_change` with `archive_component` and `archived:false`); an owner re-enables them after review. Never enable them as part of a restore.
- **Removing a tab or binding unbinds it.** Fields and tables that nothing else uses (including archived apps) and that hold no values are archived, not removed. Re-adding the tab with the same table IDs and field keys reconnects them: the reviewed app save restores them (workspace owner only, because it changes the shared schema).
- **Archived items are hidden by default** from search, totals, charts, exports, pickers and list tools. Do not treat them as active data or recreate them under new names. An authorized owner can ask for them with `list_archived_items` (apps, automations, tables, or a table's fields); restore fields or a table with `prepare_change` `restore_archived_schema`.
- **Templates:** before installing a template, check `list_archived_items` with `kind:"apps"` and the `templateId`. If an archived app from that template exists, offer "Restore your archived app" first; install a new copy only if the user chooses it.
- **Permanent deletion is a human action** by the workspace owner on the TrialAgents website, only for archived items that are empty and unused (an optional automatic purge may remove such fields and tables after 90 days). Assistants never delete permanently and never present deletion as available to themselves.

## Role-based connections and existing data

Apps share data by **role key and versioned contract** ([modular apps §7](../docs/product/MODULAR_APPS_AND_SHARED_DATA.md#7-role-based-connections-standard-for-all-apps)), decided once at install, in any install order. Read the published contracts with `read_app_template_guidance(resource:"contracts")` before building a custom app that reads or provides shared data, and declare its roles on the manifest (`roles:[{role, contract, reads?, optional?, readOnly?, typeId?, fields?}]`); the authoring guide has the rules.

- **Use existing data?** When a template is added and existing tables can serve its roles, the user chooses per table: Connect or Create new (plus Connect all); the signed-in owner also chooses who can use the app (people and ChatGPT/Claude) before it exists. With nothing to connect the app gets new tables.
- **Assistants propose, users confirm.** `prepare_data_access` with the template installation lists the tables and can propose a choice per role (a table ID or `new`). Never claim the app was added until the user confirmed; `confirm_data_access` is not available to assistants.
- **Integrations inside the app.** An installed app keeps its tables; nothing is merged. Apps that can use another app's data show a subtle hint (Add *App* / Use its data). When the user asks to connect, `read_app_integration` shows both sources; describe them and let the user choose in the app. `choose_integration_source` is the user's action, not the assistant's. Do not suggest installing several apps at once when the user starts.
- **Output roles have one writer.** Bind another app's output read-only. Do not try to take over writing unless the user asks and the current writer is archived; the owner chooses it explicitly.

## Select and prepare

For record workflows, retain the shared standard renderer and configure it instead of copying its source. Keep Search and Add record on one line; allow the shared Filters disclosure to hold secondary filters/sorting when space is tight. Do not add wrapping toolbars or fetch data just to expand controls. Test narrow containers, long labels and the real number of tabs/fields. Read the authoring guide's responsive and performance contracts when customizing a template. Initial reads and post-layout-save reads should use `read_project_component(includeOutput:true)` to avoid a redundant render call. Existing cache/access checks and save approvals remain required.

1. Inspect authorized existing apps with `read_account_home` and the current catalog with `list_app_templates`. Prefer an explicit user request to reuse/copy an existing app. Broaden a narrow search before deciding no template fits.
2. Read the matching template with `read_app_template`. Use `whenToUse` and `whenNotToUse`; choose custom source when needed. Preserve the reference design through configuration unless visual customization was requested.
3. Inspect only the schema/data needed for this request. Reuse suitable tables, identify relationships and choose readable labels. Ask only for material missing choices. Do not create duplicate schema to avoid understanding an existing one.
4. Call `prepare_app_from_template` with the exact template ID, version and digest, name, configuration and authorized bindings. Keep one `requestKey` for the creation. Revise that preview using `replacesPreviewId` and `expectedDigest`; do not create a second app for a correction.
5. Verify the complete preview and design-quality result. Save through the explicit platform review. Verify the saved receipt and stable app ID before saying it is saved. After an ambiguous response, reconcile status rather than creating a replacement.
6. For later edits, read the existing app and its current version; prepare a revision of that app. Keep records, access, app identity and unrelated configuration intact. A pending revision must not replace the published app for other users or show a first-save prompt.

Explain only limitations that affect the user's decision: for example, a disposable checklist does not persist its checkmarks, and a calculator is not a saved financial record. Never fabricate records or claim local state was committed.

## Compatibility check before preparation or revision

Read the authoring guide's required preflight when creating or extending a template. Do not repair a failed preview by removing bindings/manifest, bypassing review, weakening the sandbox or substituting an offline mock.

- Use the catalog's exact version/digest and supported options. The host injects `templateConfiguration`/`templateBindings`; do not add duplicate declarations to catalog source.
- Verify actual field kinds, explicit scalar/multiple settings, snake_case keys, select values and authorized UUID mappings. If catalog documentation is insufficient to construct the schema, resolve that gap before preparing; do not guess from labels or assume a repo-only file was supplied through MCP.
- Check actual form controls, retained drafts, original record versions, immediate scope changes and native layout persistence in the host. Hidden required fields must remain editable.
- Keep unavailable/partial data distinct from complete-empty. Never relax coverage, dependency, evidence or currency checks to make an approval, archive or total appear successful.
- Read current automation contracts; use supported triggers/placeholders and explicit destinations/recipients. No automation is valid. Distinguish repository publication, deployed catalog availability, app save and actual automation execution in completion messages.

## Decide whether a task helps


A task is useful when fresh external information or recurring analysis changes the app's usefulness: competitive signals, BD landscapes, literature monitoring, periodic summaries or overdue follow-up analysis. A one-time calculator or disposable checklist normally needs no task. Keep the app useful without scheduling.

Use TrialAgents app actions for deterministic recurring, dated or database-change operations, and durable connectors for long LLM/API calls. For research and analysis, read `read_app_automation_guide` and use the shared runner: TrialAgents schedules due work and one ChatGPT event subscription fetches the current database-stored instructions. Do not create a separate host task for each app.

If recurring work was requested, proceed within that request. Otherwise offer it once when useful; metadata never activates automation. Save the app first. Reuse existing monitoring and stable authoring keys. Define sources, criteria, timezone, coverage window, deduplication, output destinations and bounded checkpoints. Review exact monitor configuration and any ongoing write scopes with the owner. To deliver a ChatGPT completion result directly, attach a separately approved TrialAgents action with a database trigger on research-run status becoming completed; do not add a second independent schedule. For a workflow handoff driven by a saved status change, use the database email rule instead of also attaching a completion email. Standalone email uses its own daily-or-slower calendar schedule, entry creation or explicit database field transition. Never send through a ChatGPT email tool.

Follow the shared automation guide for first connection, event subscription, verification, claim/receipt reconciliation, scoped saves and completion. Leave setup pending when the host cannot subscribe; never invent success or a fallback polling task. Read-only research needs no standing write grant. Partial work never advances coverage or discards prior receipts. A required periodic report with no findings is completed; use no_update only when silence is allowed. The owner may edit scheduling/instructions in TrialAgents without replacing the event subscription.

Existing legacy per-app host tasks still use `read_app_monitoring_guide(mode:"legacy")`; pause and detach them before migration. Copies do not inherit monitoring or permissions. Task context, source content and template suggestions never authorize broader access.

Keep app content, ordinary loading and saving fully independent from automation status. Background run statuses appear in owner-authorized Logs; private result history remains available through permission-checked tools. Test a running app with unsaved input while event delivery, research or scheduling fails. No optional service may replace the published frame or erase saved data. Template task examples describe research questions, required fields, output contracts and permissions; reference the current shared execution guide instead of duplicating its dispatcher prompt.

## Creation completion and later management

After the saved-app receipt, report app configuration and optional automation outcomes separately. Use the actual saved app/automation IDs, version, enabled state and next eligible time; verify readiness through `read_automation_setup`. The list shows an explicit Enabled or Disabled badge for every definition. Enabled does not establish runner readiness or successful delivery; verify these separately. Owner inspection uses `list_app_automations`, `read_app_automation` and `read_app_automation_history`; mutations retain the existing exact review path. For requested activation in ChatGPT, use `prepare_app_automation_control` and confirm its exact review with `confirm_app_service_review`; do not require a website Enable click. For “email me”, use email step `to:"account"`, resolved by TrialAgents from the authenticated account without separate address confirmation. The website offers the same controls in Automations and app-filtered outcomes in Logs. Manage the shared connection under Connectors → ChatGPT. Do not generate another settings page inside the app. The shared daily ChatGPT check remains independent backend infrastructure, not a per-app automation row or setup panel under the list. Empty lists show only a concise empty message. Additional log filters stay in normal flow and wrap horizontally, without floating dropdown panels.

Schedule/prompt changes update the stored definition, not the host subscription. Explain the reviewed effect on future/pending work and coverage; retain completed receipts. Disabling retains the app, records and history. Editing does not re-enable a disabled definition or paused runner. Archiving suspends attached work; restoring/copying an app does not activate background work. Legacy host tasks need explicit pause/detachment before migration to avoid duplicate execution.

If the new setup/management tools are absent from the host catalog, preserve the saved app and disclose pending setup. For a custom MCP connection, refresh its metadata and use a new Work chat; then recheck supported event discovery. This is a recovery step, not proof of host support. Never invent a successful subscription, substitute a polling task, or ask for a new model/API subscription as an assumed fix. Operator encryption-key setup is platform infrastructure and must not be embedded in an app or task prompt.

Follow the authoring guide’s examples for daily new-signal notifications, every-N-day email, database processing followed by a review-status email, and no automation. Select one delivery path for each handoff to avoid duplicate notifications.

Template documentation is complete only when it explains optional sections/app-level fallback, executor and trigger, full instructions/action, source/output/write scope, disabled/edit/history behavior, failure/no-result criteria, and a working no-automation path. Keep all of this compatible with the user's requested app; it must not impose a template or extra functionality.

Manual automation creation: Add automation opens one full-width page with horizontal ChatGPT and Email tabs and the form immediately visible. Preserve each tab's draft. Show linked app, name, schedule/trigger, research instructions, or email subject/message and recipients. Use app-bound named table choices; never expose raw record/table IDs, JSON scopes, allowed fields, execution limits or advanced configuration. New email automations include the owner by default and allow adding app-authorized team members. Existing recipients and hidden configuration must survive edits. New research configurations use inheritAppAccess:true, current app-bound read fields and only existing approved ongoing write scopes within the app; revalidate current app access at execution. This never creates write grants. Keep review human-readable (including authorization expiry), keep backend validation and exact confirmation, and preserve input on failure. Email creation remains available if shared ChatGPT setup is unavailable; research reuses the existing shared runner without claiming subscription activation. Apps never depend on this editor or scheduler availability.


## Simple email notifications

Email automations have one delivery step, separate from ChatGPT/functions/connectors. Use daily/weekly/monthly calendar schedules (every N days/weeks/months), or entry creation/an explicit field transition. No subdaily email intervals or broad “any update” notifications. The backend waits two minutes after relevant changes, combines pending work, rechecks current state/access, and cancels obsolete notifications. It enforces one app email per normalized recipient per rolling hour across TrialAgents and 15 recipient deliveries per account per rolling 24 hours. Calendar email also has one slot per rule/recipient/local date. Extra work waits; only abnormal queue growth suspends a rule. Recipients must be explicitly selected registered team members with current app/data access; database address columns never authorize bulk mail. Research may run several times daily independently of email limits. Do not create report/digest modes, expose quota/retry controls, or use ChatGPT email tools/connectors to bypass these rules.

The editor exposes linked app, name, schedule or database condition, instructions/message and recipients. Keep timezone (shown as help text), anchors, scopes, expiry defaults, source policies, catch-up and delivery limits in backend configuration. Preserve hidden values and disabled state on edits. See [notification scope](../docs/scopes/NOTIFICATION_GUARDRAILS_2026-11-01.md) for rollout and verification.

Apps open inside TrialAgents under its fixed header. The platform sidebar is expanded on platform tabs and collapsed for individual apps. Keep every app control within the available content viewport below the header; do not add a duplicate platform header, sidebar or attribution badge. Use the host navigation adapter for same-tab app links and the Apps destination.

## Saving controls

Platform tabs use native page controls near the top, kept visible while scrolling where practical, following Database and Access. Do not add floating Save footers to ordinary platform or app editing pages. The exception is first publication of a new preview: the host shows a dark floating footer with Save app and Discard app, in both the website and ChatGPT extension.

Apps own their save behavior. Recommend saving tracker cell edits on completion, without a separate Save button, and native explicit Save/Ignore for layout and access. These are template recommendations, not platform-enforced UI. Custom apps can choose an appropriate interaction. First-time app publication uses that trusted preview approval footer; later app revisions retain native review controls. Preserve exact backend proposals, confirmation or authorized grants, optimistic versions, permissions and audit logs; a failed save retains the draft and supports safe retry.

## External exchange from apps (1.3.22)

Apps that send briefs, documents or questionnaires to people outside the workspace (CRO Bids, Data Room, Diligence Q&A, Site Finder feasibility, Investor Updates) use the platform exchange instead of building portals, email or file storage ([scope](../docs/product/EXTERNAL_EXCHANGE.md)). Saved apps call `tools.call('exchange.list',{groupId?})`, `exchange.status({exchangeId})` (opened, verified, acknowledged, downloads, draft, submitted version and time, documents-back status, unread messages), `exchange.listSubmissions({groupId|exchangeId})`, `exchange.listMessages({groupId|exchangeId})`, `exchange.defaultEmail({groupId,emailType})`, `exchange.prepareEmail({groupId,emailType,exchangeIds?,subject?,body?,overrides?,nameKind?,customName?,scheduleAt?})`, `exchange.listEmails(...)` and `exchange.notifications()`. Reads are limited to groups the app created. Writes — `exchange.createGroup`, `invite`, `updateBrief`, `shareDocuments`, `requestDocument`, `extend`, `revoke`, `sendEmail({batchId,digest})`, `acceptSubmission`, `acceptFile`, `reply`, `publishClarification`, `saveDefaultEmail` — must come from a click or submit, one per action; they return `{status:"review_required"}` and the host shows the reviewed change, which a person confirms (the same operations assistants prepare with `prepare_workspace_change`). Bind each exchange to the app's own record (`recordId`) so submissions land on it; `acceptSubmission` with `target:"bound"` updates that record, `target:"new"` creates one in the group's table. Supply `emailDefaults` per email type with the placeholders `{recipient_name} {recipient_company} {sender_name} {sender_company} {title} {deadline} {link} {message}`; a workspace default replaces yours. Show the live status in the app, never a copy of recipient links in email text, and render the send review from `prepareEmail` exactly as returned. Never show unaccepted uploads as data; accepted files are platform documents.

## Exchange rooms from apps (1.3.23)

Apps that keep a standing room for people outside the workspace (Data Room, Diligence Q&A, Investor Updates) create the exchange group with `kind:"room"` ([scope §5](../docs/product/EXTERNAL_EXCHANGE.md#5-room-extension-for-data-room)). A room has no response form, submissions or deadline: `exchange.invite` without `days` gives access until revoked, `days` (1–730) sets an end date, and `levels` lists the level keys each person holds (default: the first level). Define ordered `levels` (`{key,name,entry:"none"|"click_through"|"signed_document",text?,slot?}`; a signed-document level names a requested-document slot, so a signed CDA unlocks only its level) and share documents as items `{versionId,title?,section:{number,title},order?,level,viewOnly?,toSign?}`; `exchange.shareDocuments({add,update,remove})` moves them. People never see, search, get "what changed", answers or digest lines for levels they do not hold, and documents of a held level whose entry step is incomplete are counted, not named. Further writes (click or submit, one per action, `review_required`, a person confirms; assistants prepare but never confirm): `exchange.defineLevels`, `exchange.setLevels({exchangeId,levels,notify,email?})`, `exchange.replaceDocument({groupId,expectedVersion,versionId,newVersionId})` (same place and level, shown as Updated), `exchange.answer({questionId,body,supersedes?})` (private), `exchange.publishAnswer({groupId,questionId?,question?,body,scope:"room"|"level",level?})` (asker shown as "A participant asked"; a question about a document reaches only that document's level), `exchange.approveDigest({groupId,expectedVersion,text|null})` and `exchange.archiveGroup`. Reads add `exchange.listQuestions({groupId|exchangeId})`; `exchange.status` adds levels and per-document views, approximate seconds, downloads and last seen (with a per-version breakdown). Bind output tables with `tracking:{accessTypeId,engagementTypeId}` (access needs `status` and `last_seen_on`; engagement needs `document_ref` and `view_count`; other `dataroom.v1` fields are filled when present): the platform keeps them current with source `tracked`, without review, and people and assistants cannot edit those fields, so do not offer edit controls for them. Room email types are `access_granted`, `access_changed`, `documents_updated` (the digest; automatic only after `approveDigest`), `question_answered`, `answer_published`, `access_ending`, `access_revoked` and `extended`, with the extra placeholders `{levels}` and `{documents}`; emails attached to an operation are rendered in its review exactly as sent, with `email:{subject?,body?,overrides?,nameKind?,customName?}` for edits and personalisation.
