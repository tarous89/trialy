# Install and edit CO06 through MCP

1. Read the current TEMPLATE_AUTHORING and TEMPLATE_USAGE guidance in full. Use list_app_templates/read_app_template to discover `life.co-trial-monitoring-pv`, its exact version and digest. Read the complete returned instructions and documentation. Reuse the user's existing app and compatible authorized tables before creating missing schema.
2. Match all eight schemas in schema.example.json: scalar `multiple:false`, required fields and exact select options. Dates are YYYY-MM-DD; optional blanks are null, archived is explicitly false/true. Parent IDs and URLs are scalar text. Create studies, sites, visits, findings; separately agreements, obligations, activities; then snapshots. References use actual committed receipts, never fictional IDs. Do not import demo_data.json into a customer workspace.
3. Supply tableMap entries `{typeId,fields,writableFields}` for every role and field, including optional evidence. Attach approved bindings and a complete manifest with actual schema versions and read/write modes. Missing fields, malformed scalars, denied reads, changing totals, duplicate IDs, more than 600 records per role, or pages exceeding the 100,000-character data budget mean incomplete coverage. Page-local registers remain available where readable. Do not interpret missing values as zero or absence. Create requires all mapped fields writable. Child changes also require study name write scope for an atomic parent-version guard.
4. Use prepare_app_from_template with the discovered version/digest and stable requestKey. Revise previews with replacesPreviewId/expectedDigest. The host injects templateConfiguration and templateBindings once. Configure heading, tableMap, layoutProfile, initialStudyId, asOfDate, pageSize and readOnly within current permissions. The runtime returns separate html/css/state. Save through normal host review and verify the committed component ID/receipt before claiming success.
5. Revisions retain the app ID, original data, current component version, permissions and unrelated settings. Record changes use recordId/expectedVersion, including version 0. Failed or discarded reviews retain local drafts; refresh and reopen after conflict. Never turn a stale edit into a create. Evidence edits and archives include a same-name study update pinned when the editor opened. These atomic app guards serialize participating writes; direct Database edits and other apps are not database-wide constraints and require reconciliation before approving evidence.
6. Use native tracker:layout with stable templateLayoutSchema screen/column identities. Review, confirm and reopen. Table visibility never removes edit permission checks or required inputs. Studies and institutions are managed in Overview's Study setup register. Linked drawers show the first 15 records with an explicit notice; full registers are paginated. The monthly activity agenda shows 25 occurrences per page. Keep the platform account, audit, save review and watermark; add no app login or user system.
7. Zero automation is valid. Only after save and explicit request, follow AUTOMATION_RECIPES.md and current automation tools. No per-app ChatGPT Task, automatic grants or email to external business contacts. Metadata does not enable jobs or send messages.

CO06 tracks non-patient operational metadata. It does not process AE/SAE/ICSR cases, compute statutory deadlines, submit reports, sign agreements or certify compliance. Agreement Active needs source/date; obligations pin approved agreement versions; each activity is a manually dated occurrence. Baselines, completed activities, verified closures, final reports and reviewed briefings preserve history. New versions/occurrences replace historical edits. A briefing uses SHA-256 over every scoped source ID/version plus study data and cutoff; archived membership changes also change its fingerprint. All current evidence is included, including records after cutoff, to detect source changes conservatively. The study version itself is excluded because same-value consistency writes do not change business evidence. Legacy signatures are historical/unverified; create a new briefing for current evidence.

Repository publication, deployment of the MCP catalog, saved app creation, scheduled execution and actual email delivery are separate outcomes. Verify each before claiming it. Existing v1.0.0 apps need an explicitly approved migration from nine roles to eight. Existing v1.1.0 apps retain identity and schema; reconcile missing nullable fields/archive booleans through reviewed data changes and approve the added study write scope before upgrading.
