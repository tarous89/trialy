# Pipeline 1.0.0 (`life.pipeline`)

Pipeline is the platform version of the standalone Pipeline prototype in [prototypes/pipeline](../../../prototypes/pipeline/README.md). It is a portfolio planner for a biotech team: programs, milestones, activities and decisions connected with their deliverables, risks and changes. It keeps the prototype's screens, workflows and rules, and runs on TrialAgents instead of in one browser.

It is a draft catalog version. The catalog sync imports it as a draft. It is not in `templates/catalog-seed.json` until the owner approves it.

## What changed from the standalone prototype

| Prototype | Platform version |
| --- | --- |
| Records and organizations in browser local storage | `pipeline.items` and `pipeline.events` tables; organizations and their contacts are the shared core `organizations` and `people` tables. Changes save at once with `records.save`, with Undo. |
| Attachments as base64 data in the browser | TrialAgents documents through the platform upload (`data-trialy-document`). The record keeps the document version and file name. |
| Approval by the owner's typed name, no identity check | The same rule (completion needs approval for the named owner), using the TrialAgents account. The app records the owner and date. The record history shows who approved. There is no sign-in, user list or identity of the app's own. |
| Settings: currency, date format, milestone lookahead, reminder lead time, six per-person email switches | Settings holds only app settings, for the app's owners: budget currency and date format. The lookahead and reminder fields and the email switches did nothing in the prototype (it had no email delivery) and are gone. |
| Digest: prepared example reports | Weekly and monthly digests built from the records (changes, deliverables, open risks, decisions and milestones due, completions, approvals waiting, items past their forecast deadline). They can be saved to an archive. |
| Own header, host menu, design-review dialog, resizable dialog drawer | The platform header. The record form is the kit side panel; the page behind it is inert. |
| Explicit cross-item dependencies (seed data only; the prototype's form edited only parent and child links) | Dependencies are the parent and child links the form edits. Each is stored on the child (`parent_rule`, `parent_outcome`). |
| Events created inside a new plan draft were staged until its first save | A new plan item reopens right after its first save. Child items and events are added then, because they need its record ID. |

Everything else stays as the prototype has it:
- the eight screens, filters and More filters;
- forecasts from dated changes;
- risk rollup through prerequisite chains and ancestors;
- dependency gating with decision outcomes;
- the completion review queue;
- status derivation from deliverable evidence;
- delete blocked while records name the item;
- Duplicate, and Ignore changes.

## Data

See `documentation.dataContract` in `catalog.metadata.json`. In brief:
- **Lists stored as text.** Multi-valued links (affected items, organizations, team members) are stored as text lists of record IDs or names, because platform relationships are scalar.
- **Changes.** A change's revised dates and budgets are a JSON object keyed by affected item.
- **Derived values.** Forecasts, risk exposure, event counts and the approval queue are derived, never stored.
