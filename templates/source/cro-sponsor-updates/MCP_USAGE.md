# Install and revise CR05 through MCP

1. Read current TEMPLATE_AUTHORING and TEMPLATE_USAGE guidance in full. Discover `life.cro-sponsor-updates` with list_app_templates/read_app_template and use its exact version/digest and complete instructions. Reuse the user's existing app and compatible authorized tables before creating missing schema.
2. Match all eight schemas in schema.example.json: scalar multiple:false, exact required fields and select choices, database text for notes/URLs and parent IDs, ISO dates and explicit archive booleans. Optional blanks are null. Create sponsors, projects, then milestones/deliverables/actions/updates, then reports/distributions. Use actual committed record IDs, never demo IDs. Never seed fictional examples into a customer workspace.
3. Supply tableMap entries `{typeId,fields,writableFields}` for every role/field. Attach current authorized bindings and the full manifest with actual schema versions and read/write modes. Missing optional fields are incomplete coverage, not empty evidence. Creation requires all mapped fields writable; child changes require project name write access and project changes require sponsor name write access for atomic consistency checks.
4. Use prepare_app_from_template with exact discovered version/digest and a stable requestKey. Revise the same preview with replacesPreviewId/expectedDigest. The host injects templateConfiguration and templateBindings once. Configure heading, tableMap, layoutProfile, initialProjectId, initialPeriod, asOfDate, pageSize and readOnly. Return separate html/css/state. Save through host review and verify the committed receipt/component identity before claiming success. Reconcile missing receipts before retrying.
5. Later revisions preserve the same app ID, current app version, data, permissions, unrelated settings and manifest. Record proposals use recordId and the original expectedVersion, including zero. Parent versions are captured when editors open; child proposals include a same-name parent update to serialize related evidence changes. Stale, revoked and discarded changes retain drafts. Reopen and reconcile after a conflict; never turn a stale edit into a create. These guards cover participating app writes, not arbitrary Database edits or other apps; reconcile external changes before approval.
6. Use native tracker:layout and stable templateLayoutSchema screen/column identities. Review, confirm and reopen the saved layout. Hidden table columns remain available in forms/details; presentation never changes permissions. Manage sponsors & projects lists all authorized parent records. Missing selected-project access never silently selects a different sponsor's project. Directories and registers paginate; linked details show the first 15 with a link-through instruction to the full register. Keep search, Filters and Add on one line. The platform owns account/auth, watermark, audit and save review.
7. For delivery, preserve original milestone baselines and require reasons for changed targets. Submitted deliverables need actual sponsor evidence/date before Accepted. Accepted inputs require a previously Submitted version, independent reviewer and chronological review date. Accepted inputs/deliverables, approved/rejected decisions, approved reports and confirmed distribution records are historical and cannot be archived through the app.
8. Create a report Draft to capture source IDs/versions, coverage and SHA-256 fingerprint. Move through In review before Approved. Require every expected team's latest revision to have valid accepted evidence and an independent dated report sign-off. The fingerprint includes project business data and all relevant source IDs/versions for the selected period/cutoff; same-name parent guard writes do not change it. Sources must still match at proposal time and the parent version must match at confirmation. If evidence changed, copy to a new report revision and review again. Legacy fingerprints remain historical; do not silently rewrite old approvals. Log distribution only after an actual manual event using date, recipient role, channel and confirmation evidence. No external sponsor email is sent.
9. Zero automations is valid. After save and explicit opt-in, follow AUTOMATION_RECIPES.md and current host automation tools. No per-app ChatGPT Task, automatic grants or sponsor/contact recipients. Template metadata cannot activate schedules or delivery.

Coverage is bounded to 600 rows per role and 100,000 JSON characters per read page. Unknown totals, duplicate IDs, changed totals, invalid scalars or missing/denied pages withhold authoritative totals and report approval. Report source references must fit 50,000 characters; oversized reports fail visibly without writes and require a narrower authorized dataset. Display labels may be shortened with an ellipsis; full values remain in details/editors. No patient-level content, external account system, clinical conclusions or inferred sponsor acceptance.

v1.0.1 preserves the eight-role schema. For existing v1.0.0 apps, approve an identity-preserving upgrade and the parent consistency write scopes; reconcile omitted nullable values/archive booleans through reviewed data changes. Never import the sample records or overwrite historical reports. Repository publication, live catalog availability, app save, automation execution and message delivery must each be verified separately.
