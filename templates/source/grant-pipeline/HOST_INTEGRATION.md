# Host and MCP integration

1. Read current `read_app_template_guidance` authoring and usage resources through every `nextOffset`, then `read_app_design`. This release was validated against guidance 1.3.9 and the repository's actual schemas/runtime.
2. Discover `life.grant-pipeline`, read exact version 1.0.1, and retain its digest. Use the current supported template preparation/confirmation tools. The catalog source never declares `templateConfiguration` or `templateBindings`; `AppTemplates.operation` injects them exactly once. Retain the host manifest and watermark.
3. Reuse suitable authorized tables or create the four scalar schemas in `schema.example.json` through reviewed database operations. URLs, narrative and references are text; every field is `multiple:false`. Physical keys are snake_case. Optional empty date/number values are null. Preserve exact select options and required fields. Never seed fictional data.
4. Create parent opportunities first, then criteria/applications, then milestones. Replace relationships with committed receipt UUIDs. Map all logical fields to actual readable physical fields and grant only authorized writes. Use current table schema versions and supported field kind/mode in the manifest.
5. Set `tableMap` to a JSON string of `{role:{typeId:<actual UUID>,fields:{logicalKey:physical_key},writableFields:[<authorized logical keys>]}}` for opportunities, criteria, applications and milestones. Restrict backend access appropriately; filters or hidden screens do not restrict access. Missing mappings/unknown totals/denied or short pages/arrays/over-budget reads are incomplete, never zero. The app reads at most two pages of 100 per role; search and pagination cover that loaded window.
6. Prepare, preview and confirm one saved app with one request key. Verify its actual saved component ID/version and reopen. If a response is ambiguous, reconcile the original preview/receipt before retrying; never create another app or duplicate record to recover. Revise that same component with expectedVersion; retain bindings, history and permission checks.
7. Exercise all six screens, an empty first-record flow, the named form controls and record review, Ignore/Close, a stale edit/archive and native layout. `data-ui-state` is on each input/select/textarea; it only enables transient drafts. Submit values use `input.event.form`. Drafts survive validation/proposal failures and remain drafts until the trusted host receipt. After confirmation reopen saved output; do not resubmit a retained create draft after ambiguous confirmation.
8. Native `tracker:layout` uses the stable single-line `templateLayoutSchema` and `layoutProfile`. It edits heading/order/visibility, never data bindings or access. Hidden form fields remain reachable via Additional fields. Use native Review/Confirm and reload the saved output. Existing-record edits/archives retain the original version, including version zero.

A human Eligible decision requires all mandatory checks assessed Yes, HTTPS evidence, nonfuture assessment dates and named reviewers. Return every linked Eligible application to Pending before changing its opportunity/check evidence. Existing relationship IDs are immutable. Archive blocks live dependents. These are app-level guards, not database foreign keys or constraints on independent database edits; reconcile independently edited records before relying on decisions.

An Open call needs verified source/date/deadline. A changed previously recorded deadline requires a new notice version and verification date; same-day re-verification is allowed. Submitted/outcome records require a completed submission date. Awarded requires a positive verified amount, notification date and official award evidence. Amounts require explicit currency and existing amounts cannot be silently relabelled. Funding review keeps currencies separate and withholds totals when a submitted/decided request lacks amount/currency. Awards are not cash received. `asOf` is a reference date for comparisons, not a historical data snapshot.

The app uses existing TrialAgents account, permissions, review and persistence. It creates no auth, subscription, email service, scheduled task or hidden network integration. App-level sections are the supported access fallback. Optional automation setup is independent and cannot interrupt app loading or erase drafts. No deployed MCP/real ChatGPT-host execution is claimed by local acceptance tests.
