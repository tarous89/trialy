# App services release

The builder contract is [APP_SERVICES.md](../resources/workspace/references/APP_SERVICES.md), also available through `read_app_services` on MCP. This release adds no app-specific authentication system or seat purchasing flow.

## Automation management

The [revised app configuration scope](product/APP_CONFIGURATION_AND_AUTOMATIONS.md) places platform actions and ChatGPT research definitions in one app-linked Automations destination. Keep executor and trigger independent. TrialAgents still owns email, deterministic jobs and approved connector/LLM calls; the ChatGPT connection is not required for those independent jobs. Research-to-email uses the existing approved completion dependency, with separate outcomes and no duplicate schedule.

Expanded platform rows edit typed action, timing, mappings and recipient policy through the same schema/review as MCP. The lifecycle offers disable/enable/edit/history, with retirement through parent app deletion and preserved receipts/data. The management adapter reuses existing action/monitor stores and review APIs. Standard calendar actions now support daily/weekly/monthly cadence, stable anchors and month-end policies. Editing preserves disabled state and unchanged database event cursors. Optional service failures remain isolated from app reads, saves and rendering; real access revocation still applies.

## Operation

Apply migration 046 using the existing migration login. `npm run db:migrate` also provisions the existing restricted web/worker roles and grants the new tables/functions from `ops/runtime-role.sql`. Existing web and worker services are reused. Do not deploy the worker without migrations and runtime role provisioning.

Configure a domain-restricted Resend sending key as `APP_NOTIFICATION_RESEND_API_KEY` on the worker. Register `https://platform.trialagents.com/notifications/webhook` for `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, `email.failed`, `email.suppressed`; put its signing secret in `RESEND_WEBHOOK_SECRET` on the web service. Keep secrets outside git and app source. The sender is fixed to `notifications@trialagents.com`. The web service only enqueues requests; it does not need the sending key.

The worker uses existing PostgreSQL for its durable queue. Three external-job loops run independently of short function execution; one slot is reserved for email. Each external job has a deadline, lease and token. Heartbeats extend leases. Lost connector leases become unknown and are never automatically replayed. Email retries use a stable provider idempotency key, stop before the provider's 24-hour window, and preserve terminal receipts. An interrupted request may have executed externally; cancellation cannot retract it.

Webhook verification uses exact raw bytes, a timestamp bound, constant-time HMAC comparison, and an append-only deduplicated database insert before acknowledgment. Delivery events may arrive out of order; terminal complaint/bounce/suppression states take precedence over sent/delivered. Suppression is global to the sending platform. Run history and job inspection never return stored provider credentials.

Limits: 1,000 external jobs per workspace per rolling day; action-specific daily limit defaults to 100; connector limits still apply. 64 KiB request and response size; background timeout max 30 minutes. This supports ordinary LLM API requests, not unlimited model outputs or token streaming. Provider monetary limits must be configured in the provider account.

Public links have isolated identities with no login credentials and no direct database browsing. Generated code retains its isolated renderer and capability allowlist. Public routes explicitly restrict calls and change previews to the shared app. Team invitations verify the invited email and possession of the token; existing broader permissions remain independent. Revoking a share removes only its grant, preserving separately edited grants.

## Validation

`tests/app-services.test.ts` exercises restricted production roles, exact approval, durable email retry, duplicate delivery events, suppression precedence, revoked actions, committed database triggers, occurrence deduplication, cycle prevention, LLM-shaped nested requests exceeding ten seconds, public app isolation and reviewed editing, and email/account matching.

`tests/visual/app-services.spec.cjs` exercises the sharing controls, public navigation, refresh persistence and revocation on desktop/mobile. Existing connector, runtime-role, access and function tests remain required.

Deploy the existing web and worker from the same commit. Verify their exact live deploys, web `/health`, MCP `read_app_services`, worker `app_services_ready` and continued worker heartbeat. A successful mock LLM call is not evidence of paid-provider acceptance; customer provider credentials remain user configured.

## Published apps and drafts

App preparation writes only owner-scoped preview rows. Saved app routes, public links and the normal app list use the committed component; ChatGPT can recover its own drafts separately. Preparing or revising a draft never changes the published component. Confirmation checks the exact digest and current saved version, then atomically commits the update and its receipt. Stage schema changes with the tracker update so its schema and app publish in one transaction.

Custom draft evaluation has one separate bounded slot; published custom apps retain two execution slots and per-app concurrency keys. A draft cannot occupy a published app slot. Periodic checks compare the viewer's effective access to that app, not unrelated workspace changes. Approved updates load at the existing route when the viewer has no local edits; local edits remain visible until the viewer chooses to discard and load the update. Only actual local edits trigger leave warnings. Access revocation still clears protected content immediately.

Public links follow compatible published revisions, retaining their original frozen data grant. Publishing does not broaden a public link's access. A draft never appears on the public route.

## App deletion and part removal

Deleting an app from Apps archives it (see Archive first below). Migration 059 extends atomic app cleanup to removed data/function bindings. Removing a tab from its data bindings retires affected app-owned research/actions and their completion follow-ups, and cancels pending occurrences, action runs, notification batches and queued jobs. Hiding a tab that remains bound does not delete its workflow. Shared runners, credentials, connectors and reusable functions are not app-owned and remain available. Already dispatched external effects cannot be recalled.

After workflow cleanup, the existing app save transaction may **archive** (never remove) unused empty fields if the actor has owner/schema access. The cross-owner dependency check (`trialy_security.unused_app_fields`, backed by `archive_usage`) sees all records (including archived rows) and every app that is not permanently deleted, **including archived apps**, even when RLS hides them from the caller. Missing, null, empty string and empty array are empty; zero, false, whitespace and other values are data. Shared bindings, derived references, views, external links, active scopes, reusable functions, automations, cross-table links and connector dependencies protect fields. No records or audit evidence are deleted. Data-bearing schemas retain their remaining fields. Schema revisions and audit events record every cleanup. Automatic cleanup does not broaden access or change general schema migration rules.

### Archive first (migration 060)

Migration 060 amends 053/059 per [modular apps §6](product/MODULAR_APPS_AND_SHARED_DATA.md#6-archive-first-apps-automations-and-database). Nothing is permanently removed as a side effect.

- **Archiving an app** (`archive_component`) no longer runs field cleanup and no longer soft-deletes automations. Its research and actions are suspended (`archived_with_app_at`, disabled/paused, CHECK-enforced) and their queued and running work is cancelled. The app's bindings keep protecting their fields. The review lists the tables that stay and the number of paused automations.
- **Restoring an app** (`archive_component` with `archived:false`) restores its automations **switched off** for owner review. A name clash adds "(restored)". Bindings to permanently deleted items are listed in the review (`archiveReview.unavailable`) and dropped only after confirmation. Fields the app binds that were archived are restored in the same transaction.
- **Archived fields** move from `entity_types.fields` to `entity_types.archived_fields` (definition, `archivedAt`, `archivedBy`, `appId`). Values stay on records. Because the active schema no longer contains them, they are excluded from Database, pickers, search, totals, charts, CSV exports and assistant schema reads. A table whose fields are all archived is archived (`archived_at`) and excluded from table lists. The full workspace backup export (`/export`) still contains every row, as a recovery snapshot.
- **Automatic restore:** a reviewed app save (`save_component`, `restore_component`, `create_tracker`, or re-adding a tab) that binds archived fields or tables restores them first. The preview's `archiveReview.restores` lists them, and confirmation checks that it is unchanged. Restoring changes the shared schema, so it needs the workspace owner. `update_type` that redefines an archived key supersedes the archived definition. Owners can also restore from the archived list with the reviewed data operation `restore_archived_schema`.
- **Permanent deletion** (`POST /organization/archived/delete`, website only; never an MCP tool) is restricted to a human workspace owner. Apps must be archived. Deleting one leaves a tombstone (`deleted_at`), retires its automations, archives the fields only it used, and keeps its tables and records. Tables and fields must be archived, empty and unused (`trialy_security.archived_item_usage`); the server returns a one-line reason otherwise. Archived automations are deleted only with their app. Deleted tables keep their row as a tombstone; revisions and audit stay.
- **Optional purge:** with `ARCHIVE_PURGE_ENABLED=true`, the worker's hourly maintenance calls `trialy_security.purge_archived_schema()` (worker role only). It removes fields and tables archived for at least 90 days that are still empty and unused, and never populated or bound items. Off by default; lists show "Deletes automatically on …" only when enabled.
- **Listing:** `list_archived_items` (MCP and `GET /organization/archived`) returns archived apps, automations, tables or a table's fields, with restore/delete eligibility, only to people who can restore them (workspace owners; for apps also the app's creator). Default lists (`list_project_components` without `includeArchived`, `list_app_automations`, `list_tables`, schema reads) exclude archived items. Template installation returns `archived_app_available` until the user restores the archived app or chooses `createNew`.
- **Logs:** `workspace.archive_component`, `workspace.restore_archived_component`, `app.deleted_permanently`, `automation.archived_with_app`, `automation.restored_disabled`, `field.archived|restored|deleted_permanently|purged` and `table.archived|restored|deleted_permanently|purged`.
- **Backfill:** fields removed by 059 cleanup are recovered into `archived_fields` from the immutable audit before-state, and schemas emptied by 059 become archived tables. Automations soft-deleted when their app was archived (053/059) become suspended and disabled; those retired earlier by binding removal stay retired.

In the interface, Apps, Automations and Database (tables, and fields on a table's page) show a subtle "Show archived … (n)" link below the list only when there are items the viewer can restore. Expanded, the archived rows appear muted below the list with an "Archived" label, Restore and Delete. Delete is disabled with its reason when not allowed, and inside ChatGPT or Claude it points to the website. Text stays at the design system's muted ink (≥ 4.5:1). The expanded state is remembered for the session.

The shared composer uses Trigger → Worker/connector → Setup. Assistant workers use their own runner; email and connector actions remain independently executable by TrialAgents. Current connector UI offers approved operations with scalar inputs; existing mappings and additional saved steps remain intact. Editing a saved workflow preserves its worker and ID; use a new workflow for a different worker.
