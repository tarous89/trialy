# Connected resources

Issue #5 implementation. Existing generic components remain compatible. New trackers, forms and visualizations use `resourceKind` and a version 1 `manifest`. Every declared binding must have a manifest field (id, typeId, field, schemaVersion, kind, mode read/write, optional label). Scope is project by default or explicitly workspace. Schema changes stop execution until bindings are reviewed again. Display-label changes do not rename database fields. Copies preserve contracts; restores preserve the selected revision's contract.

`read_workspace_schema` exposes bounded schema metadata to authorized workspace members, including schema-only restricted fields. It never includes entries, counts, options, formulas, source code or defaults. Workspace AI disablement and workspace membership still apply. Existing data tools retain their stricter value policies. `find_field_candidates` ranks type-compatible schema candidates; it does not decide semantic identity. Read all pages, prefer existing columns and relationships, and check meaning, context and units before proposing new schema. A restricted field is not an excuse to duplicate its contents.

For trusted data controls, frontend-js returns `controls:[{slot,fieldId,recordId}]` alongside html/css/state and places `<span data-trialy-slot="slot"></span>` in its HTML. The server resolves the value and edit policy from the manifest and current database; the frame creates the actual input. Changes prepare the normal reviewed write and never silently commit. Ordinary generated inputs on connected resources are disabled unless marked `data-ui-state` for filters/layout state. Generated text/charts may use only declared permitted reads; arbitrary prose cannot be mechanically certified as database-derived. Real data literals in source remain subject to existing conservative source sharing rules.

Project-scoped reads and edits are restricted to linked records; new records created through a connected resource are linked transactionally to its project. Another tracker reads the same updated record on refresh. Visualization resources cannot have write manifest fields, attach execution bindings, invoke functions or propose record changes. Existing generic code is not retroactively classified as a tracker.

Backend access policies remain separate from generated code. This change does not grant SQL access to any client or bypass existing value checks. PostgreSQL schema constraints validate persisted classification; business permission checks currently live in the shared backend service. Production runtime role separation is prepared in ops/runtime-role.sql but the existing owner connection must be replaced through a separately verified credential rollout. Do not call this full PostgreSQL-level tenant/field isolation.

Restricted-data automation execution is not silently delegated: schema discovery enables planning, but existing execution checks continue to deny unauthorized value access. A separately approved executor/output authorization model is required before arbitrary code can run with stronger data access than its requesting actor.


## Resource screens and release boundaries

The shared shell provides Projects, Trackers, Forms, Visualizations, Database, Automations and Changes & permissions. App Settings stays outside the plugin; generated frames retain their own styles. Database loads metadata first and one selected page at a time, projects permitted columns before search/sort, hides restricted table counts, bounds pages and rechecks access before returning. The table editor is explicitly workspace-wide. Public-link review currently covers the whole workspace.

Public forms submit once without a visitor preview step; team acceptance remains reviewed and creates a new record linked to the form project. Existing-record response editing is not exposed. Published form definitions are immutable: replace a link and revoke the old one after review. Schedules can be paused/resumed or replaced with a separately reviewed schedule.

Guest save defaults to an existing eligible owned workspace when available. Compatible table reuse requires matching field keys, kinds, cardinality, declared options and required fields, with a reviewed schema version. The owner confirms semantic suitability. New tables in that destination need an explicit reason. Different-key mappings need adaptation before import; no unsafe generated-source string rewrite of field names is attempted. Rows are new records, never implicit merges. The atomic receipt records the destination mapping.

Remaining release acceptance: production least-privileged role rollout and PostgreSQL isolation; real authenticated browser/ChatGPT host acceptance and measured payload/latency baselines. Service-level permission integration tests are not substitutes for these checks.

## Follow-up acceptance — 23 October 2026

The standalone app now revalidates the signed-in session on focus/visibility return and every 30 seconds while visible. Database pages re-fetch on those events. Saved frontend code uses a small `check_component_access` response (ID/version only) to revalidate current permissions without rerunning generated code or transferring source/rows. Failed access checks clear the frame and prevent reopening cached source/history; changed revisions require reopening. This is bounded periodic revalidation, not instantaneous push revocation; data already downloaded cannot be recalled from a recipient.

`npm run db:runtime-audit` and the optional `REQUIRE_RESTRICTED_DATABASE_ROLE=true` startup check are now implemented for both web and worker. The production flag has not been enabled against the known development owner connection. See [DATABASE_ROLE_ROLLOUT.md](DATABASE_ROLE_ROLLOUT.md) for the private-network provisioning, migration-job and credential steps, and the remaining separate RLS requirement.

It uses separate actual browser accounts, verifies stored tracker values, revokes a member's field access and checks the frame/source editor disappear, invalidates a revision, and revokes the owner session while the app is open. No injected actor or production write is used. A one-row Database response in that synthetic local run was 434 bytes and about 14 ms; this is not a production latency benchmark.

The connected production Trialy MCP `open_workspace` authenticated successfully and returned the authorized workspace/schema. This verifies the live authenticated tool boundary only, not manual ChatGPT iframe navigation/approval-return acceptance.
