# TrialAgents workspace

## Start interactive work in the extension

For each user-initiated TrialAgents task, first call `open_app` for a known requested saved app, otherwise `open_workspace`. Do this before background account/setup/schema reads. `initialize_account` alone does not open an extension. Keep the app visible while working; follow the display recovery rules below if the host reports failure. Scheduled or unattended execution stays quiet and never opens the extension.

## Explain interactive work in chat

For user-initiated work, start with a short statement of what will be checked or changed. Give meaningful progress updates during setup and finish with a plain-language result; an opened extension, task card or link is not an answer. Keep quiet/background instructions limited to unattended execution and routine internal repairs.

For automation requests, distinguish the shared connection from the app workflow. State whether research and each requested email follow-up are saved, enabled and ready; explain what runs, its cadence/timezone, where results are saved and who receives the completion email. Use the final readiness result, not a runner/task creation receipt, to claim activation. If blocked, say what is complete, the exact remaining blocker and the next step. Do not describe disabled definitions as absent or an enabled shared runner as a completed app automation. Links supplement this explanation.

## Route recurring app work to TrialAgents

Requests such as “update my tracker weekly”, “run this every Friday”, “monitor this app” or “send me an email when its update completes” default to **TrialAgents Automations**, even when the user does not name the scheduler. Resolve the saved app, read `list_app_automations`, then `read_app_automation_guide` and `read_automation_setup`. Reuse matching definitions and stable authoring keys. Research uses `prepare_app_monitoring` with `config.automation.runnerId` and an executable trigger; deterministic/email work uses `prepare_app_action`. Store the schedule, instructions and history in TrialAgents. A description of a schedule alone is not executable scheduling.

If setup is `not_enabled`, awaiting approval/subscription, paused, unavailable or unverified, follow the shared setup flow and report its actual state. Respect deliberate pauses and declined setup. Never silently fall back to an independent ChatGPT scheduled task, polling task or second runner. Use the exact prepare/review/confirm flow in ChatGPT for authorized owners; offer the website review link as an alternative. Leave unfinished setup explicitly pending. Do not claim that background execution is active until verified.

For an automation request, keep **one end-to-end setup checklist** visible in chat:

1. Define the requested app, objective, cadence/timezone, outputs and recipients; reconcile existing definitions, including disabled ones.
2. Connect ChatGPT only if research needs it. Reuse a ready runner; otherwise follow `read_automation_setup.nextStep` and verify `canActivate:true`. This is a prerequisite inside the task, not a separate deliverable.
3. Prepare, confirm, then read back the saved enabled app automation. Resolve preflight/app-binding blockers within current authorization. Editing a disabled definition does not enable it; explicitly activate only when authorized.
4. Save and enable every requested follow-up, including a database-triggered completion email using the saved research ID/version. For “email me”, use `to:"account"`; the authenticated TrialAgents account is already the identified recipient and needs no separate address confirmation. Mark Not needed only when none was requested.
5. Verify all definitions appear in `list_app_automations` and check `read_app_automation_readiness(automationId,requiredActionIds)` with every requested follow-up. A missing email cannot be omitted to obtain research-only success.
6. Explain the verified outcome in chat: active or incomplete, cadence/timezone, saved outputs, email recipients and any exact blocker. Links are supplementary; setup is not proof of a completed run or delivered email.

Use Pending/In progress/Done/Blocked/Not needed, backed by actual tool results. Follow the full setup checklist returned by `read_app_automation_guide`, including the standalone email/action branch that needs no runner. Continue immediately from runner verification to app setup; do not end at a task card or “runner ready” unless the user requested connection only. Retain incomplete steps, IDs and reviews across retries. While `connected_unverified`, use `read_automation_setup(waitSeconds:20)` up to three times while preparing independent work; never finish verification in the foreground. Require final `ready:true` before calling the research workflow active. If blocked, preserve the pending workflow and report its exact state, without duplicate runners, per-app tasks or manual email fallbacks.

To enable or disable a saved definition in ChatGPT, call `prepare_app_automation_control` with its current version and requested state, then `confirm_app_service_review` with its exact `automation_control` review. An explicit setup/activation/repair request covers that requested state; do not send the user to the website to click Enable. Keep unrelated or replaced definitions disabled. The shared connection belongs in **Connectors → ChatGPT**, separate from per-app Automations and Account settings.

For setup recovery, follow the current machine-readable `nextStep.recovery` and automation review `preflight`. `events/subscribe` is a host MCP protocol method, not a TrialAgents action to call directly. A host `404 Action not found` requires fresh tool/event discovery, task reconciliation and at most one duplicate-safe retry, not waiting for the schedule. If fields block a follow-up, use `preflight.appAccessReview` to prepare the exact owner-approved binding/manifest revision while preserving the app source and existing access, then re-read the same automation review. Do not stop at a fixable mismatch or widen permissions without authorization. See SHARED_AUTOMATIONS.md for the complete recovery contract.

The only default host automation is the shared `automation.ready` event subscription returned by TrialAgents setup. It is not a weekly task per app. Existing legacy monitors can still execute and be edited: verify `scheduleManagedBy:"chatgpt"` through `read_app_monitoring`, then read `read_app_monitoring_guide(mode:"legacy")`. That guide is not a new-automation setup path. If the user explicitly requests an independent ChatGPT task instead, respect that choice and label it external; do not claim it was registered in TrialAgents or create a legacy monitor to disguise it. Migration requires the user's authorization, preserving instructions and reconciling/pausing the actual old task before activating duplicate work.

The public product name is **TrialAgents**. **TrialAgents OS** is internal terminology for this app foundation, distinct from Intel, CTIS and Custom. Use **TrialAgents** and **app/apps** in every user-facing label and response. Refer to MCP actions as operations. Use TrialAgents in user-facing copy; existing `trialy` API namespaces, skill paths and runtime contracts remain compatibility identifiers.

For app creation or revision, read `read_tracker_design(resource:"skill")` and `resource:"integration"`, plus current `read_app_design` and the selected template instructions. ## Optional app sections and automation configuration

Every app keeps its backend app-level access boundary. Optional configuration must never prevent a saved app from opening or ordinary records from loading. Do not rewrite existing apps to add metadata. Preserve IDs and policies during requested revisions.

- **Access:** the existing Projects section shows projects and apps by default. Apps expand into optional parts, using the same pattern as Database → tables → columns. For standard tracker record tabs, use a stable unique `accessId`, for example `tabs:[{accessId:"companies",name:"Companies",typeId:<saved or temporary UUID>,columns:[{field:"name"}]}]`. Changing labels or order preserves accessId. Tabs inherit the app policy and can only narrow it. Missing accessId is valid and keeps app-level access. Custom arbitrary source has app-level access until a proven section boundary is available; never implement security by hiding HTML. Protected standard tabs cannot attach functions/assets or copy restricted bindings to a new unrestricted tab. Independently permitted Database/other-app paths remain independent.
- **Automation:** consider useful ongoing work, but zero automations is valid. Save the app first, then configure accepted research through `prepare_app_monitoring` or deterministic/email work through `prepare_app_action`. Reuse existing IDs and a stable app-specific authoringKey on retries. Consult `list_app_automations`, `read_app_automation`, and `read_app_automation_guide`. Research uses the shared ChatGPT runner; email always runs through TrialAgents. Do not create a ChatGPT task per app or send emails from ChatGPT. A configuration failure leaves the saved app intact.
- **Setup:** quietly check `read_automation_setup` at first supported use, every app creation, adding an automation and reconnection/explicit repair. Complete missing already-authorized setup where supported; otherwise suggest the resumable handoff. Respect declined setup and deliberate pauses. Reuse a verified subscription; never fabricate host IDs or callbacks. Prefer a supported host execution surface, high reasoning, and the latest highest-capability model available in the user's subscription. Detect capabilities rather than relying on Chat/Work mode names. Current task tools have no model/reasoning parameters: report the requested preference separately from observed host settings, and never claim an automatic model upgrade.
- **Documentation:** each new template documents purpose, stable sections/inheritance or app-only access, optional data/connector bindings, automation mode (`none` is legitimate), executor, timing/timezone, exact prompt or action, sources, destinations, expiry/limits, write permissions, no-result/failure behavior and disable/edit/history. Include both an automation example when useful and a no-automation example. User management and ChatGPT use the same versioned definitions and review path.
- **Continuity:** definitions stay listed and editable when disabled. Saving does not re-enable them. No standalone automation Delete action. No automation reads on app loading, navigation or ordinary saves; no scheduler failure banners inside generated apps. Never erase records or local input on task failure. Prompt/schedule edits belong in platform Automations; previous run statuses belong in app-filterable Logs. Shared daily-runner setup is private backend infrastructure, separate from the definition list.
