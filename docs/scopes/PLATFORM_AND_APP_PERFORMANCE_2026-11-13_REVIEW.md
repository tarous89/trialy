# Review: platform and app performance recommendations

**Reviews:** [PLATFORM_AND_APP_PERFORMANCE_2026-11-13.md](PLATFORM_AND_APP_PERFORMANCE_2026-11-13.md). **Date:** 13 November 2026.

**Method:** I read the source at `main` `f49c8c7` and checked each claim against it. I did not run profiling or measure anything in production. Where I disagree with a rating, it is expected impact judged from the code, like the original document's ratings.

**Markers:** ⬆ prioritize or raise the impact · ⬇ impact is overstated, or the gain is too small for the effort right now · ✎ the description is inaccurate or incomplete · ✓ agree, possibly with implementation notes.

## Summary

- **Mostly accurate.** Every "Observed" claim I checked holds. Examples: the 30 s rechecks, the progress bar after 150 ms, `max-age=0`, static files served after the session middleware, a forked sandbox per execution, the cap of 2 published custom executions, and the silent post-save reload failure.
- **Most important missing items:** the database wrapper opens a transaction for every query (N1), and session and auth add database work to every request, static files included (N2). Both are cheap to fix, affect every page, and make the document's query counts look 3–4× smaller than the real number of round trips.
- **Biggest current UX risk:** one sandbox concurrency cap is shared by all web, ChatGPT and Claude users of a server process. The third simultaneous custom-app interaction is refused at once. P11 should be split so that a queue (P11a) ships early.
- **The app figures come from empty fixtures.** The "13/10/9 reads" show the fixed overhead, not what happens with real data. With data, Runway-style "read everything" hits hard limits (88/100 calls, 4 MB read budget, 15 s). The forecast becomes truncated (incomplete) or the read fails.
- **Overstated:** P02, P05 (no gain for the ChatGPT/Claude embed), P10 (opening from Home already uses one request) and RW2/PG2 calculation caching.

## 2. Additional red flags affecting current users

1. **Shared sandbox cap (P11).** Two published custom executions run per process, shared across web, ChatGPT and Claude. An assistant rendering an app can make a web user's click fail with "This interface is busy", and the other way round. On one starter instance, this is the platform's ceiling for custom-app throughput.
2. **No abort propagation.** Abandoned requests keep running on the server and keep their sandbox slot, which compounds flag 1. Superseded Home rebuilds (from P03's double trigger) also run to completion.
3. **Idle tabs cause continuous load (P03 + N2).** A visible Home tab rebuilds account Home every 30 s and touches the session row on each request. This grows with users × open tabs and competes with real work on 0.5 CPU and a 10-connection pool.
4. **Correctness cliffs with populated data.** The sandbox allows 100 calls, a 4 MB cumulative read payload and 15 s wall time per execution (`runtime.ts:5,19`). Runway allows itself 88 calls. Read-everything templates with larger tables will show *truncated* (incomplete) forecasts or fail with "Read budget exceeded". The empty-fixture profiling cannot see this.
5. **Silent stale view after save (P12).** This happens today, as described above.
6. **Lazy chunks break across deploys** if P05 ships without P04's `fallthrough:false` and a preload-error handler.

## 3. Missing recommendations

| ID | Issue | Recommendation | Impact | Complexity |
| --- | --- | --- | --- | --- |
| **N1** ⬆ | `Postgres.query()` wraps **every** standalone query in its own transaction (`src/db/database.ts:10`). That means a pool checkout plus `BEGIN`, `set_config(...)`, the query and `COMMIT`: 4 round trips per query. It affects Home, rechecks, records reads and auth. | Run read endpoints (Home, lists, app open, metadata rechecks) inside **one request-scoped transaction**, so the context is set once. **Never hold it across a sandbox execution** (15 s wall, pool of 10). Alternatively, send `BEGIN` and `set_config` in one round trip. Keep `is_local=true` so RLS context can never leak across pooled connections. | **High** (platform-wide) | Low–medium |
| **N2** | Each request touches the session (rolling cookie plus a store `touch` UPDATE) and runs a `session_version` SELECT. That includes static assets and every 30 s poll. | P04 removes this for assets. For the API, limit touch writes to, for example, once per hour per session (the rolling cookie can still refresh). Keep the `session_version` check, because it enforces revocation. | Medium | Low |
| **N3** | Abort propagation (flag 2). | Pass an `AbortSignal` from `req.on('close')` into `execute()` and into long Home reads. | Medium (High under contention) | Low |
| **N4** | Sequential capability calls (P07 note). | Add a `records.readMany` batch capability, and skip `count(*)` when `offset>0` within the same execution. Optionally add an index on `records(workspace_id,type_id,created_at,id) WHERE state<>'archived'` (today only `(workspace_id,type_id)` exists); this is low priority at current data sizes. | High for custom apps | Low–medium plus template adoption |

## 4. Suggested revised order

1. **Baseline:** P14 with the corrected counters and populated fixtures.
2. **Quick wins (each about 0.25–1 day):** P04 → N2 → P03 (quick part) → P06 → P12 (basic) → P11a + N3.
3. **Shared read efficiency:** N1 → P01 (`previews:false`, set-based queries) → P08.
4. **Custom-app pilot:** N4 + P07 + P09 on Runway, then Programs and Contracts. Revise Fundraise inside PR #137.
5. **Later:** P11b, P02, P10, P05 (only after P04), P13 follow-ups, §2.8 per-app work by measured rank, and last of all RW2/PG2 calculation reuse.
