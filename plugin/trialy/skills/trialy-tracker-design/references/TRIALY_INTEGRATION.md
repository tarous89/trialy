## Connected resource contract

Before choosing columns, call read_workspace_schema and find_field_candidates, paging through relevant schema. Strongly prefer compatible existing fields and relationship paths. Consider context, type, units and cardinality, not just labels. Create a field only if no existing field correctly represents the fact; explain why in the schema review. Schema-only fields cannot be read without authorization and must not be copied to evade restrictions.

Save new account-backed trackers with resourceKind: tracker and a version 1 manifest. Each manifest field names id, typeId, field, schemaVersion, kind and mode (read/write), plus optional local label. Every data binding must be covered. Default scope: workspace for an independent tracker in Home. Use project scope when the user intends linked project records only; project placement alone never changes data scope. Use resourceKind: visualization with read-only fields for dashboards. Read docs/CONNECTED_RESOURCES.md for the current enforcement boundary.

For data entry, return controls:[{slot,fieldId,recordId}] from frontend-js and place a span with data-trialy-slot matching each slot in the generated HTML. The server supplies current values and the trusted frame supplies inputs and reviewed edits. Mark only transient filters/layout inputs data-ui-state. Do not hand-code business inputs with local-only Save behavior. Calculations and charts must use declared live reads. Newly created records use the reviewed records.propose path; project linkage follows that save.

## Responsive execution

The approved renderer runs once against bounded backend reads, then a fixed, CSP-hashed browser copy handles tabs, search, sort, details and layout over that authorized snapshot. These local actions do not call MCP or reread tables. Pagination beyond the loaded page, reopening, writes and permission rechecks use the backend. Search/sort applies to the loaded page, as labeled. Exact legacy default renderers are upgraded on display; custom source is preserved. No eval, arbitrary browser scripts, network access or policy bypass is introduced. This is an HTML template implementation, not a separate generic table UI.

Default new trackers to all columns visible and multiple-value editable fields (except dates/status/boolean and scalar calculated or unique identity fields). Preserve reused schema cardinality. Previews remain private, reopenable from Home, and labelled Preview until saved, discarded or expired (24 hours). Choose an existing matching project from context or null before preparing a preview; Save has no project picker. The visible save confirms that exact destination.

## Simple-app extensions

Use `prepare_app` for a custom app without selecting a category. It preserves existing component IDs, data bindings, reviews and version checks. A calculator can omit tables. Existing template kinds stay internal compatibility metadata.

`input.route` supplies a validated path plus optional recordId/page. Use plain anchors for internal pages, canonical returned app URLs for cross-app links, and ordinary permitted external links. The shell owns history, refresh, sign-in return, dirty-edit warnings and its footer. Generated code stays isolated; no script tags, browser DOM, fetch or packages are enabled. `tools.call('records.get',{recordId})` is a saved-app-only bound read with current scope checks.

Generic HTTPS operations use `tools.call('connectors.call',...)`, declared access and mapped fields. Configuration and credentials live in Connectors. Secrets never appear in source, the model or frame. Free-text disclosure and external effects require exact trusted review, and returned data saves through existing record review. See the workspace skill's Connectors section for request keys, completion events, quotas and unknown outcomes.

## Optional app sections and automation configuration

Every app keeps its backend app-level access boundary. Optional configuration must never prevent a saved app from opening or ordinary records from loading. Do not rewrite existing apps to add metadata. Preserve IDs and policies during requested revisions.

- **Access:** the existing Projects section shows projects and apps by default. Apps expand into optional parts, using the same pattern as Database → tables → columns. For standard tracker record tabs, use a stable unique `accessId`, for example `tabs:[{accessId:"companies",name:"Companies",typeId:<saved or temporary UUID>,columns:[{field:"name"}]}]`. Changing labels or order preserves accessId. Tabs inherit the app policy and can only narrow it. Missing accessId is valid and keeps app-level access. Custom arbitrary source has app-level access until a proven section boundary is available; never implement security by hiding HTML. Protected standard tabs cannot attach functions/assets or copy restricted bindings to a new unrestricted tab. Independently permitted Database/other-app paths remain independent.
- **Automation:** consider useful ongoing work, but zero automations is valid. Save the app first, then configure accepted research through `prepare_app_monitoring` or deterministic/email work through `prepare_app_action`. Reuse existing IDs and a stable app-specific authoringKey on retries. Consult `list_app_automations`, `read_app_automation`, and `read_app_automation_guide`. Research uses the shared ChatGPT runner; email always runs through TrialAgents. Do not create a ChatGPT task per app or send emails from ChatGPT. A configuration failure leaves the saved app intact.
- **Setup:** quietly check `read_automation_setup` at first supported use, every app creation, adding an automation and reconnection/explicit repair. Complete missing already-authorized setup where supported; otherwise suggest the resumable handoff. Respect declined setup and deliberate pauses. Reuse a verified subscription; never fabricate host IDs or callbacks. Prefer a supported Work chat, high reasoning, and the latest highest-capability model available in the user's subscription. Current task tools have no model/reasoning parameters: report the requested preference separately from observed host settings, and never claim an automatic model upgrade.
- **Documentation:** each new template documents purpose, stable sections/inheritance or app-only access, optional data/connector bindings, automation mode (`none` is legitimate), executor, timing/timezone, exact prompt or action, sources, destinations, expiry/limits, write permissions, no-result/failure behavior and disable/edit/history. Include both an automation example when useful and a no-automation example. User management and ChatGPT use the same versioned definitions and review path.
- **Continuity:** definitions stay listed and editable when disabled. Saving does not re-enable them. No standalone automation Delete action. No automation reads on app loading, navigation or ordinary saves; no scheduler failure banners inside generated apps. Never erase records or local input on task failure. Prompt/schedule edits belong in platform Automations; previous run statuses belong in app-filterable Logs. Shared daily-runner setup is private backend infrastructure, separate from the definition list.
