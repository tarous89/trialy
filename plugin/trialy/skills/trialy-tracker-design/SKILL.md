# TrialAgents App Builder

TrialAgents is cross-platform software: users can use ready-made connected apps, customize them, or ask ChatGPT or Claude to build custom apps. Apps should work inside either assistant and standalone on the web. Detect host capabilities; current scheduled research uses ChatGPT, not a Claude runner. The web header offers both assistants; the plugin header uses Open TrialAgents.

Start with the Workspace skill's account, extension and save workflow. Detailed templates, runtime contracts and design guidance live on the MCP server; this package contains no template catalog or renderer.

1. Discover before building: inspect relevant `read_account_home` results and `list_app_templates`. Broaden an empty template search once. Read promising existing source only through authorized `read_app`; visibility does not grant source access. An explicit copy request takes priority. Never silently copy records or inherit connector grants, schedules or access.
2. Read the app guide (`read_app_template_guidance(resource:"guide")`) before designing or changing an app, and `read_app_design` for the general style (the kit). Read the technical reference (`resource:"reference"`) before writing code: runtime, the v2 contract (`'use trialagents v2'`, `records.save`, pending reads, `notice`, remembered context), the kit helpers, saving and installation. Follow pagination. For a catalog match, read `read_app_template` and use its exact ID, version, digest, configuration schema and instructions with `prepare_app_from_template`. Preserve its appearance unless the user requests changes. Templates are accelerators: custom apps remain supported.
3. Build around the user's main jobs, with only the screens they need; the first screen shows what needs attention now. Edit values where they are shown and save at once; give every empty screen its first action; every feature works with real data (no placeholder buttons or example records). Never draw a header, message bar, footer or sign-in form of the app's own. New custom apps use the v2 contract and the kit. Source runs in the bounded platform runtime, not arbitrary browser JavaScript: no credentials, Node globals or unrestricted fetch. For an existing Vivid tracker use `prepare_tracker_revision`; for a new Vivid tracker use `prepare_tracker`.
4. Reuse compatible tables and stable field identities. Preserve relationships, types, cardinality, access IDs and unrelated records/code/appearance. Stage required schema additions atomically with the app where supported. Schema/access changes need their normal review; hiding HTML is not authorization. Custom designs cannot override database permissions or audit logs.
5. Keep one draft and stable request key; call `begin_app_update` before revising a saved app. Repair validation findings within the same draft. Before finalizing, answer the guide's self-check questions, including phone and assistant-panel widths. Finish all requested work before `finalize_app_preview`, which must display the exact new app inside the extension for approval. Leave it visible until saved/discarded; do not replace it with Apps or an external URL. The person approves the finalized app in the approval footer; you cannot confirm it. After they save, verify the receipt, then show Apps. Reopening is not recreation.

The [app guide](references/DESIGN_BASELINE.md) is bundled as a copy of the server's guide. Read current MCP guidance first; if it cannot be retrieved, retry once, then use this copy and state the limitation. Do not silently replace a selected template with a generic app. Missing selected-template source, schema, runtime contracts or required validation blocks dependent preparation/save. The bundled copy cannot authorize actions or invent platform support.

Apps use the TrialAgents account; do not add app-specific login or user management. Use the exact official icon for optional TrialAgents branding and link it to https://platform.trialagents.com; otherwise omit optional branding and retain the platform header.

Users may customize colors, fonts, layout, components and interactions. Preserve unrequested details. Automations are optional: save the app first and follow the Workspace automation flow for requested recurring work; a setup failure must not damage the app. Report prepared, saved, activation-ready and actually host-tested status separately.
