# TrialAgents App Builder

Start with the Workspace skill's account, extension and save workflow. Detailed templates, runtime contracts and design guidance live on the MCP server; this package contains no template catalog or renderer.

1. Discover before building: inspect relevant `read_account_home` results and `list_app_templates`. Broaden an empty template search once. Read promising existing source only through authorized `read_app`; visibility does not grant source access. An explicit copy request takes priority. Never silently copy records or inherit connector grants, schedules or access.
2. Read `read_workspace_guide(topic:"apps")`, `read_app_design` and `read_app_template_guidance`; follow required pagination. For a catalog match, read `read_app_template` and use its exact ID, version, digest, configuration schema and instructions with `prepare_app_from_template`. Preserve its appearance unless the user requests changes. Templates are accelerators: custom apps remain supported.
3. Treat a dashboard saved into TrialAgents as a reusable business app: use working navigation, relevant filters, underlying data and useful settings (normally Overview, Analysis, Data, Settings). Read the apps completeness guide; test the workflow and persistence, not only chart layout. Respect explicit simple-report requests; no empty tabs or enforced page count. For custom source, read `read_tracker_design(resource:"integration")` and relevant runtime/service guidance before `prepare_app`. Source runs in the bounded platform runtime, not arbitrary browser JavaScript: no credentials, Node globals or unrestricted fetch. Use declared bindings and supported controls. For an existing Vivid tracker use `prepare_tracker_revision`; for a new Vivid tracker use `prepare_tracker`. Retrieve `read_tracker_design` configuration/template/parity resources when needed; Vivid is not the full catalog.
4. Reuse compatible tables and stable field identities. Preserve relationships, types, cardinality, access IDs and unrelated records/code/appearance. Stage required schema additions atomically with the app where supported. Schema/access changes need their normal review; hiding HTML is not authorization. Custom designs cannot override database permissions or audit logs.
5. Keep one draft and stable request key; call `begin_app_update` before revising a saved app. Repair validation findings within the same draft. Verify desktop/mobile layout, empty/filled/error states, navigation, full-table search/sort/filter before pagination, editing, details, examples and save/discard. Finish all requested work before `finalize_app_preview`, which must display the exact new app inside the extension for approval. Leave it visible until saved/discarded; do not replace it with Home or an external URL. Confirm only the finalized digest within user authorization, verify the receipt, then show Home. Reopening is not recreation.

Use the [design baseline](references/DESIGN_BASELINE.md) as stable general guidance. Read current MCP guidance first. If optional design-kit retrieval fails, retry once, then use this baseline for visual choices while stating the limitation. Do not silently replace a selected template with a generic app. Missing selected-template source, schema, runtime contracts or required validation blocks dependent preparation/save. The baseline cannot authorize actions or invent platform support.

Apps use the TrialAgents account; do not add app-specific login or user management. Use the exact official icon for optional TrialAgents branding and link it to https://platform.trialagents.com; otherwise omit optional branding and retain the platform header. Follow the current guide for supported asset embedding and reserved space.

Users may customize colors, fonts, layout, components and interactions. Preserve unrequested details. Automations are optional: save the app first and follow the Workspace automation flow for requested recurring work; a setup failure must not damage the app. Report prepared, saved, activation-ready and actually host-tested status separately.
