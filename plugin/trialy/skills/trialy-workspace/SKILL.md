# Trialy workspace

For tracker creation or revision, read ../trialy-tracker-design/SKILL.md and its integration reference first (or call read_tracker_design). User instructions and existing authorized data guide the result; defaults fill gaps. The reference is only an opened tracker, never the entire plugin UI.

## Tracker creation path

1. Require a connected account, then call `initialize_account` to resolve storage quietly. Do not call `open_workspace` or open Home for a creation request. Read the tracker design and inspect compatible schema with `read_workspace_schema` / `find_field_candidates` in the background. Reuse semantically compatible fields; schema similarity alone never justifies reading unrelated records.
2. Build the actual temporary tracker before asking the user to approve fields or a save. Call `prepare_tracker` with meaningful names and tabs. For existing tables use their saved IDs and exact column keys. For missing tables supply `newTables:[{id:"fresh-UUID",name:"Companies",fields:[{key:"name",name:"Company",kind:"text",ai:true},{key:"source",name:"Source",kind:"text",ai:true}]}]` and refer to that UUID in `tabs:[{name:"Companies",typeId:"same-UUID",columns:[{field:"name"},{field:"source"}]}]`. These are temporary definitions, not saved tables. Include only genuinely missing tables. For missing fields on a compatible existing table use `extendTables:[{typeId,expectedVersion,newFields:[{key:"follow_up",name:"Follow-up",kind:"date",ai:true}]}]` and include that field in its tab. These additions are also temporary and save with the tracker; existing fields are preserved. Do not run separate schema commits before showing this preview. References to other new draft tables are not supported in this creation bundle; do not claim such links exist.
3. `prepare_tracker` opens the designed tracker directly in the extension. Use `open_tracker_draft` only to reopen a pending draft. Do not substitute chat field suggestions, JSON, Home, or a technical database table for the visible tracker. Inspect existing projects quietly and choose a clearly matching projectId; otherwise use `projectId:null`; never create a project called "No project", "Home", or another placeholder to hold unassigned work.
4. Supply one meaningful fictional example for every empty data tab using `tabs[].example`, e.g. `example:{name:"Example biotech",source:null}` for Companies and `example:{name:"Alex Morgan (example)",source:null}` for Contacts. The top-level example remains supported for the first tab. Defaults fill omitted fields with typed illustrative values and semantic color tags. Examples stay unsaved, are excluded from real totals, and disappear from each tab as that tab gains records. Use `showExample:false` if requested. Do not use unrelated real records as examples.
5. AFTER showing the tracker, ask only whether to save it. Use the matching existing project chosen from context, or Home if none matches. Do not ask users to select a project or show a project selector in the save footer. The Save tracker button confirms the exact preview. In chat, confirm with `confirm_workspace_change`, then `open_tracker` using the receipt ID. Valid unsaved previews are also available on Home with a Preview badge until their existing expiry; they are private to their creator and never approval tasks. Saved trackers replace their preview entry. Required new tables and tracker save atomically. Discard leaves no tracker or new tables. Never claim completion without a save receipt and successful opening.
6. Show all fields by default. New fields accept multiple values unless they are dates, status fields, booleans, unique identity fields or calculated scalar outputs. Set `multiple:true` explicitly for new fields created outside `prepare_tracker`; set false for an explicit single-value customization. Preserve existing schemas when reusing columns, and request a separate migration rather than silently changing populated fields.
7. Only ask a clarification before preview when an essential ambiguity prevents a meaningful safe draft; ordinary field/design choices should be visible in the draft. Preserve existing data and permissions. Custom user designs can still use `save_component` frontend-js with the approved styling and verified database bindings.

The default template supports live bound cells, reviewed batch edits, record entry, details, page search/sort, pagination, persistent reviewed layout labels/visibility/drag order, a full-height resizable details drawer, and backend access settings. Tabs, search, sorting, details and layout edits are local and must not trigger a server render. Save/update actions use a single dark floating footer; no Advanced/reload header clutter. Template examples are display-only. Adding fields/tabs, advanced relationship creation, record duplication/deletion, table/row resizing and granular role overrides still require the relevant supported backend/UI path; do not claim unavailable controls. Layout labels never rename database keys. Users can override the template through custom frontend-js.

Call `open_workspace` when the user explicitly opens Home/Trialy. After connecting for a creation request, resume creation through `initialize_account` without navigating to Home. Render its interactive view. If authentication is needed, use the host connection flow; never request passwords or tokens in chat. Trialy signup and consent return to the registered host callback.

Require a connected account before creating any project, tracker, form, dashboard or automation. Discuss requirements before connection if useful, but use the host authentication flow before creation. `initialize_account` initializes a new account database automatically and returns its internal workspaceId. Never ask the user to create or name a workspace. Reuse the returned workspaceId; never bypass existing access restrictions or enable AI access on an existing restricted account.

Access saved account data only through authenticated tools. Do not use preview_tracker to create new drafts: it is a retired compatibility entry point. Public design guidance remains available through read_tracker_design; external public forms remain usable without login. Backend permissions apply to every operation. Never route restricted fields through chat, hidden model context or another tool. The current embedded view uses only AI-accessible data; human-only fields are not supported here yet.

For changes, use the user's current instructions to discuss and settle the action in the conversation, then prepare and confirm the exact change using its returned digest. Call confirmation tools only for an action the user authorized; never imply that a preview is saved. Use the returned receipt (or `save_status` after an interruption) as evidence. Do not create a deferred approval task, “Needs review” badge or retrospective review inbox. A completed action is complete; later corrections are new actions. Confirmation retains the AI actor and all current backend permissions, version checks and expiry checks. Background code cannot confirm its own proposals: automatic recurring writes still require a scoped, unexpired execution or maintenance grant. Owner-only account/security operations remain in Settings when the backend requires a human session.

Original document storage and extraction are separate. An unavailable or partial extraction is a quiet source-coverage flag, not proof the original is lost. When answering questions, disclose material missing coverage; do not invent content from unextracted documents.

Trialy is not fit for patient-level data. Do not claim regulatory certification, validated electronic signatures, zero-loss production recovery, or complete feature parity. Do not add patient-content screening or quarantine. Keep the user-facing intended-use notice and report actual supported behavior.

The workspace declares host entrypoints and a fullscreen preference. Automatic opening after OAuth depends on the host; never claim this was verified merely because the tool was registered.

Trialy is a foundation, not a catalogue of templates or prescribed workflows. Use `execution_capabilities` before writing code. The pinned JavaScript runtime accepts a function body with `input` and synchronous `tools.call(name, input)`; there are no host files, packages, fetch, credentials or Node globals. Declare only the needed capabilities and table IDs. Use `run_code`, then `inspect_code_run`; queued or computed is not saved. Reuse a requestKey to reconcile a submission, never for changed source/input.

`changes.propose` collects exact record writes. `schema.propose` proposes user-defined schemas/views for explicit confirmation, not standing record-write permission. Discuss the exact returned proposal in the current conversation and confirm the agreed action immediately. Do not route it to a later review inbox. Saving a function through `preview_function` and its confirmation creates an immutable source revision, separately from a grant. Invoke an exact revision; use a grantId only when the user has explicitly chosen that already approved scope. Once/future grants bind an exact revision, ONE data type, a fixed field list, schema version, expiry and maximum change count. Old pre-contract grants require renewal. `prepare_execution_control` prepares an exact grant or schedule; confirm it after agreeing its scope, expiry and effects with the user. Revoke stops future effects. Scheduling is generic code execution, not a preset business workflow.

Experiments, results and proposals expire after 24 hours and are not authoritative saves. To retain a result, preview saving it as an original file and confirm the file save. Programs can return artifacts as `{artifacts:[{filename,mime,base64}]}` within the output limit. The gateway currently supports Trialy data/schema proposals and a synthetic echo adapter. Do not claim access to other ChatGPT-connected apps, arbitrary external URLs or external side effects. A new provider needs its own server adapter and authorization.

## Projects and approved ongoing maintenance

Use `list_workspace_projects` and `prepare_workspace_change` for folders/projects, moves and renames. Confirm the agreed organization change with its exact preview digest. Organization changes require full workspace access; readers with restricted data access can see project paths for explicitly released, accessible bound components. Inherited folder/project permissions still apply. Owners can review separate human allowlists and AI access for projects/components. Moves retain existing restrictions. Do not claim a canonical merged database view is complete.

Create a new table only when the requested task involves multiple entries, repeated actions, tracking or expected reuse, including a tracker that starts with one person. Inspect existing schemas and candidates first. Use person/organization identities across tasks and keep project-specific facts separate. Use `setup_tracking` through `prepare_workspace_change` for one reviewed atomic new/existing table setup, initialRows, project links and scope. New schemas can carry an optional concept: person, organization, project or location. No fixed clinical tables are required. For a separate existing scope, prepare `save_scope` with a project, purpose, inclusion criteria, source policy, exact table/field bindings, allowed additions/updates/identity links and a batch limit. This task scope is preview-only by default (`autoWrite:false`). Longer-term permission is separate and explicit: `autoWrite:true`, exactly one type binding, specified fields/actions, and expiresAt, reviewed by the human. Schema expansion requires its own review and renewed scope approval.

When relevant new information arrives, call `list_maintenance_scopes`, inspect candidate records, and apply `maintain_workspace_records` only if the information fits an active scope. Respect purpose and sourcePolicy, not merely matching columns. Include a concise sourceLabel and interpretation explaining eligibility and uncertainty. Do not archive full conversations or fabricate missing facts. Expect a visible proposal by default. Only an active explicit single-data-type autoWrite permission can skip repeated approval, and changes must still appear in history with that grant. A returned temporary preview is NOT saved. Never create a scope or broaden fields/sources on the user's behalf without review. Reuse the identical requestKey for a retry; changed content requires a new UUID. A schemaChanged/revoked scope cannot authorize maintenance. Report saved counts only after the returned receipt.

Use `read_record_evidence` to inspect observations and identity links. A reversible identity link marks an alias/preferred record but preserves both source records and all original relationships. Use `find_identity_candidates` for textual candidates and `read_shared_identity` for the preferred record, originals, conflicting values, authorized observations and incoming relationships. Candidates are not proof of a match. Same-table links are explicit stars; direct cross-table links use reviewed field correspondence. Both preserve existing references; ordinary record queries retain originals. Bounded code can use entities.search and entities.read within declared table scopes; entities.read omits cross-table relationships. Do not silently replace conflicting facts or infer external-action authority from a match. Unlink through a reviewed proposal to correct a mistaken match.

Only information supplied through authorized tools/work can be maintained; Trialy does not monitor every ChatGPT conversation. Existing workers execute saved functions, but maintenance scopes are not yet wired as scheduled worker programs. Email/calendar adapters remain unavailable.

## Saved components and live interfaces

For standard tools use `prepare_tracker` and `prepare_tracker_revision`. Generic non-template resources retain `prepare_workspace_change` with `save_component`; new custom tracker formats require designChangeReason explaining a specific unsupported template requirement; editing saved standard source requires the signed-in app editor. Review/save before claiming persistence. Use `list_project_components`, `read_project_component`, and `read_component_history` to reopen work across chats. Move/archive/restore through explicit reviewed operations; restoring makes a new revision and retains the current project/archive state. Saved source is not permission to run code or external actions.

For standard tools, the server stores template ID plus JSON configuration and owns the renderer. Tailor the full content to the user, not the template example. Read `read_tracker_design(resource:"configuration")`. Use the approved Vivid HTML template as the first and default tracker format. Always adapt tables, columns, labels, statuses, calculations and other content to the user. Different business terminology is not a reason for new code. Only when a required interaction or presentation cannot be expressed by the template may ChatGPT choose a new custom format: explain the specific limitation in `prepare_workspace_change` → `save_component.designChangeReason`, preserve the connected resource manifest and permissions, then open the draft with `open_tracker_draft` and use the normal reviewed save. This exception creates a new tool only; it cannot replace a saved standard tracker. Ordinary revisions use `prepare_tracker_revision`. `trialy-ui` is legacy compatibility only.

The following runtime notes describe existing/custom code, not the standard authoring path. `frontend-js` custom source is a JavaScript function body receiving `input.state` and `input.event`, returning `{html,css,state}`. Escape data and use supported data-action events; no browser scripts or event handlers.

Use synchronous `tools.call('records.read', {typeId,limit:50,offset:0})` to read only fields declared in content.bindings. Use `tools.call('records.propose', changes)` with up to 50 create_record/update_record operations to request changes within those bindings. This does not save: the trusted outer workspace presents exact review/confirmation. Always describe writes as proposed until the receipt confirms success. An unsaved code preview may read bound data but cannot propose writes. Use open_tracker_draft to try the interface before saving. `run_component_frontend` is app-only.

Custom JavaScript runs in bounded QuickJS, not in the browser frame. The standard approved template additionally uses Trialy's fixed trusted browser renderer with a bounded, authorized data snapshot for instant UI interactions. Exact known template code is recognized; custom code is never evaluated in the browser. The frame renders filtered HTML/CSS; raw script tags, event handlers, URLs, frames, remote assets and navigation are disallowed. There is no browser DOM, arbitrary fetch, npm/React package environment, credentials or host filesystem in guest code. Do not claim compatibility with an unmodified browser/React app. For example, return HTML for a form and handle its event on the next invocation instead of adding an onclick handler. CSS and inline SVG can provide custom dashboards; no Trialy chart/form block type is required. Other formats remain source-only.

Default sourceAccess is workspace, requiring full field/document access because source can embed copied values. sourceAccess:bindings is an explicit owner-reviewed release of the ENTIRE source, including literals, to permitted component/project viewers with all bound fields and assets. Never choose this as a silent access-denial workaround. Historical private source stays protected; live queries/writes remain scoped. Bound-audience components cannot attach functions with workspace-wide document access. This does not provide a human-only channel inside ChatGPT. Do not work around an access denial by copying data into another component. Saved components can declare execution:[{name,revisionId,grantId?}] for exact owned functions. Their data bindings must include every readable field in the function table scopes. Without grantId, computed writes remain proposals. `invoke_component_function` queues a binding; generic run/status/cancel controls apply. A function schedule may pin componentContext:{id,version,binding}. Component changes, archives or lost access invalidate that context. Restoring code clears execution bindings. External adapters remain pending. Browser/ChatGPT acceptance of the new runtime is not verified.

## Visible history and code execution bridge

Use `list_field_changes` for per-field old/new values, actor, time and exact approval/grant. Logging begins with this update; older revisions remain in record history/Activity. `prepare_change` reverse_field_change requires changeId, expectedVersion and reason, then confirmation of the agreed action. It creates a new audited correction and never erases history. Later edits or required/derived fields can require an explicit correction instead. Schema changes and reversals never inherit standing record-write authority.

For saved frontend-js components, tools.call('functions.invoke',{binding,input,requestKey}) stages up to three bound function invocations. These are queued atomically only after the render completes successfully; return status is pending_render_completion, not a completed result. Keep the UUID requestKey in interface state and use tools.call('functions.status',{requestKey}) on a later event to read that component run. Failed render or admission leaves no queued calls from that event. Draft interfaces cannot enqueue. Run output is temporary; saving any database proposal still follows the approval/grant rules above.

## Shared project context, assets and collection

Use `list_project_records` and `list_project_relationships` for existing shared records and explicit customer-defined relationship edges in a project. Link records to projects after review; do not duplicate identities just to display them elsewhere. `list_table_mappings`, `save_table_mapping` and reviewed cross-table identity links retain column correspondence and source alternatives. `propagate_linked_values` proposes selected fields to selected current direct links; source/target versions, mapping and link state are rechecked. It never means automatic ongoing synchronization or permission to contact linked people.

Component `assets:[{name,versionId}]` refers to committed document versions. Use frontend `files.list`, `files.text({name,offset})` or `files.image({name})` for permitted named assets only. Image reads accept small verified raster originals; no external URLs or SVG/script assets. Unavailable extraction is coverage information, not lost source data. `project.records({offset})` and `project.relationships({offset})` read only the component's current project and declared type/field bindings.

For external information gathering, prepare `create_collection_link` (form or view, exact type/fields, optional questions/file request, expiry); agree its bearer-link audience with the owner before confirming and returning the URL. Anyone holding the URL can use it; do not call this verified-recipient sharing. Do not send it to others without the user's instruction. Read authorized incoming fields with `list_collection_responses`; use `accept_collection_response` to preview each exact database addition. An external response is not automatically accepted into the shared database. Use `revoke_collection_link` for reviewed revocation. Files submitted externally stay in the separate human review path until accepted. No internal approval is a regulated signature.

Build editable interfaces by default where permissions and bindings allow, with explicit proposal/save status and separate source/details pages. Changes to live fields target shared records after review; presentation changes target component revisions. Do not silently create per-view fact overrides or treat temporary interface state as saved work.


## Connected resources and reuse-first routing

Before proposing fields, call `read_workspace_schema` and page through relevant definitions; use `find_field_candidates` for compatible suggestions. Compare entity, meaning, units, cardinality, project context and relationships, not labels alone. Prefer existing columns with local display labels. Record candidates and why a new field is necessary in the visible review. An inaccessible field is a permission gap, not a reason to duplicate it. Preserve ambiguous facts; never auto-merge or overwrite.

Choose `resourceKind` tracker, form or dashboard and a version 1 manifest for new connected frontend-js resources. Read the tracker integration reference for the manifest and trusted `controls` contract. Every business field must be declared in the manifest and bindings; temporary UI controls use `data-ui-state`. Derived/chart dependencies must be declared as bound read fields. Use backend calculated fields for persistent shared calculations. Never embed real restricted data in source or represent hard-coded samples as live records. Existing generic components require deliberate classification and a reviewed manifest.

Forms: use `create_collection_link` with kind form, existing type/fields, questions and optional projectId. Outsiders submit through the link without login. Responses are unverified submissions until the owner reviews `accept_collection_response`; acceptance creates a new record, never silently updates a matching existing record. Shared general links cannot edit arbitrary records. Review/revoke links through Forms. To change published questions, prepare a replacement link and explicitly revoke the old one; links are immutable definitions. Files use the existing standalone review workflow.

Dashboards: declare read-only manifest fields and no execution bindings. Use the same records and project scope as trackers; chart calculations declare all source fields. The server rejects record writes and function invocation from visualization resources.

Automations: use `execution_capabilities` for supported tools/triggers. Use `planningOnly:true` to save a disabled definition against schema-only tables. It remains awaiting authorization and cannot run, receive a grant or be scheduled. To activate, prepare a new executable revision with valid current value access and explicit scoped authority. Never impersonate an owner. The Automations screen supports functions/revisions, grants, interval/daily/event schedules, pause/resume and run inspection. Replace a schedule through an explicit reviewed new schedule; pause the old schedule to avoid duplicate runs.

Navigation is Home, Database and Logs, with Settings at the bottom (opens the app from ChatGPT). Home combines project banners, type filters, search, preview grid and detailed list. Open saved resources from Home; custom resource styles remain independent. Automation failure highlights belong in Logs only. There is no pending-review navigation or notification center. Database loads a table/page on demand using `read_database_table`; schema-only access reveals no row counts or values. The global project filter applies to resource listings and Database; the public-links inbox explicitly covers the whole workspace. Keep generated resource HTML/CSS inside its frame; shell colors do not override it.

Previously issued temporary previews can still be recovered before their expiry and saved through their existing account handoff. Do not create new anonymous previews.

## Projects and tools

Use the actual names **project, tracker, form, dashboard, automation**. Use **tool** as the collective label. The sidebar has one **New** menu with Project, Tracker, Form, Dashboard, Automation and Custom tool. Projects are optional organizational containers. Create an independent component with `save_component` and `projectId:null` (or omitted); use a workspace-scoped manifest and existing permitted database bindings. Do not invent an empty project to satisfy creation. Public form links and saved functions can also be created independently. For new trackers, forms, dashboards or automations that need a project-specific data scope, obtain that project explicitly.

Use Home to drag a tracker, form, dashboard or automation onto a project or onto **All** to remove its project assignment. Unassigned work appears under All, never in a placeholder project. The Move to menu provides the same operation without dragging. In chat, obtain the tool's `source`, `id` and `placementVersion` from `read_workspace_home`, then call `move_tool` with `toolId`, `source`, `expectedVersion`, `projectId` (null to remove), and `confirmed:true` only for the user-requested move. Refresh after a stale-version failure. Organization does not change record scopes, inherited access restrictions, public-link behavior, function bindings or execution grants. Never claim that moving a tool shares its data. Data scope and sharing changes require their own explicit authorized operations.

## Account and creation entry points
New accounts receive Project 1 once during initial setup. Rename or delete it on request; do not recreate it after deletion. Projects remain optional. New → Project creates a simple folder directly: require only a name, with optional description and Access. Other types open the filterable template gallery; Custom tool is always first and continues in ChatGPT. Template setup explicitly asks whether to reuse existing tables/fields or create new empty tables. Never silently copy records when reconnecting a source. Show a preview before saving user-requested new work. Database access is configured per colleague at table and column level by the owner; apply the same permissions in the app and plugin.


## Source mapping and template setup
Use Dashboard as the display name; keep `resourceKind: visualization` for compatibility with saved API data. In tool settings → Layout, display a Database source column beside each tool field. Reconnecting a source changes bindings and updates type, cardinality, options and derived/read-only behavior from the authorized database field. Keep existing records in place. Review incompatible actions or custom code before changing them; never bypass database permissions. Standard tools support reviewed mapping changes directly; custom code must be revised with its bindings. Automation templates save a reusable read-only report; running and scheduling remain explicit actions.

## Standard tools: configuration-only contract
For trackers, forms and dashboards, use prepare_tracker and prepare_tracker_revision. Read read_tracker_design(resource:"configuration") for typed inputs. Tailor all content; keep the shared UI. Raw source changes remain unavailable to AI for existing standard tools. New exceptional custom formats follow the documented designChangeReason path and reviewed save. Do not relabel a standard tool as generic.
