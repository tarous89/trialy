
# Building and redesigning TrialAgents apps

Read this when creating an app or changing its design. The account, display and save workflow is in the main [skill](../SKILL.md). Detailed templates, runtime contracts and design guidance live on the TrialAgents connector; this plugin contains no template catalog or renderer.

1. **Discover before building.** Check relevant `read_account_home` results and `list_app_templates`; broaden an empty template search once. Read existing source only through authorized `read_app`; visibility does not grant source access. An explicit copy request takes priority. Never silently copy records or inherit connector grants, schedules or access.
2. **Read current guidance.** Read the app guide (`read_app_template_guidance(resource:"guide")`) before designing or changing an app, and `read_app_design` for the general style (the kit). Read the technical reference (`resource:"reference"`) before writing code: it covers the runtime, the v2 contract (`'use trialagents v2'`, `records.save`, pending reads, `notice`, remembered context), the kit helpers, saving and installation. Follow pagination to the end. For a catalog match, read `read_app_template` and use its exact ID, version, digest, configuration schema and instructions with `prepare_app_from_template`. Keep its appearance unless the user asks for changes. Templates are starting points; custom apps remain supported.
3. **Build around the job.** Use only the screens the user's main jobs need; the first screen shows what needs attention now. Let people edit values where they are shown and save at once; every empty screen offers its first action; every feature works with real data, with no placeholder buttons or example records. Never draw a header, message bar, footer or sign-in form of the app's own: the platform provides them. New custom apps use the v2 contract and the kit. Source runs in the bounded platform runtime: no credentials, Node globals or unrestricted fetch. For an existing Vivid tracker use `prepare_tracker_revision`; for a new one use `prepare_tracker`.
4. **Preserve data and access.** Reuse compatible tables and stable field identities. Keep relationships, types, cardinality, access IDs and unrelated records, code and appearance. Stage required schema additions together with the app where supported. Schema and access changes need their normal review; hiding HTML is not authorization. Custom designs cannot override database permissions or audit logs.
5. **One draft, one finalization.** Keep one draft and a stable request key; call `begin_app_update` before revising a saved app. Fix validation findings in the same draft. Before finalizing, answer the guide's self-check questions (every screen serves a job, nothing platform-owned is recreated, fewest clicks, a first action on every empty screen, every feature works, fast, works on a phone and in the assistant panel). Finish everything requested, then call `finalize_app_preview` once. In Claude apps that show interactive MCP Apps, leave that preview visible until it is saved or discarded. In Claude Code, describe the finalized preview and its digest in text and ask before confirming. Confirm only the finalized digest within the user's authorization and verify the receipt.

The [app guide](DESIGN_BASELINE.md) is bundled here as a copy of the connector's guide. If the connector guidance cannot be retrieved, retry once, then use this copy and say so. Do not silently replace a selected template with a generic app. A missing selected template, schema, runtime contract or required validation blocks the dependent save. The bundled copy cannot authorize actions or invent platform support.

Apps use the TrialAgents account; do not add app-specific login or user management. For optional TrialAgents branding, use the official icon linked to https://platform.trialagents.com; otherwise keep the platform header. Users may customize colors, fonts, layout, components and interactions; preserve details they did not ask to change. Save the app before any optional automation and follow the automation section of the main skill. Report prepared, saved and actually displayed status separately.
